# Outline 看板同步（进度与待办 → 看板服务）

## 概述

看板服务是一个**无需登录、只读**的网站，嵌入在每个项目的「看板」文档和全员可见的「总看板」文档集里，提供时间线、表格、看板、风险四个视图，页面顶部显示「最近一次会后的变化」。网页上不能编辑，所有写入都由本技能完成。

**数据以 Outline 为准。** 项目的进度和待办写在「进度与待办」这篇文档里：它的正文（**首页**）是当前全貌，由 outline-promeeting-update 每次会后按固定模板整篇重写；它下面每次会议一篇**会议子文档**「YYYY-MM-DD 会议主题」，只记那次会议的变化。本技能按以下步骤把首页搬到看板上：

1. **前置检查**：看板通道（MCP 或 CLI）、本人身份、Outline MCP
2. **定位项目**：找到直接包含「进度与待办」的那一层文档或文档集；还是旧结构（「进度追踪」「待办事项」）的，先提示迁移
3. **首次处理**：登记项目；**征得同意后**创建「看板」文档；询问是否加入总看板（默认否）
4. **读取与抽取**：只读首页的五张表，每行一条，逐格照读
5. **编号**：沿用首页已有编号；只给空着的编号格编新号
6. **规范化**：按固定对照填字段；出处是首页，来源会议是会议子文档
7. **同步与写回**：先 `dryRun` 自查；通过后**只用 patch** 把新编号填进首页空着的编号格，再正式同步；然后整理项目目录顺序（第十节）；最后汇报变化和看板链接

首页每行一个编号、一个负责人、一个截止、六个状态词之一，所以抽取几乎是机械的：表 → `type`，编号 → `code`，负责人 → `owners`（负责人＋执行人），截止 → `due`（原文、时间窗、精度），状态 → `status`，进展 → `statusNote`，关联 → `parentCode` / `relatedCodes`。逐格规则、截止写法表和完整示例都在 `references/extraction.md` §0，**第 4～6 步开始前先完整读一遍 §0**。extraction.md 的附录（§1–§13）是旧结构的规则，只在用户坚持同步没迁移的项目时才读。

核心原则：**只从首页抽取（会议子文档和会议纪要只查阅）；逐格照读，不符合模板的行不猜、列出来；写回时只填空着的编号格，不改其他任何文字；状态只看状态格；先 dryRun 再同步；有疑问先问，不猜。**

## 一、前置检查

### 1. 看板通道（MCP 优先，没有再用 CLI）

- **看板 MCP**：调用 `board_version`。能调通就全程用 `board_*` 工具。
- **CLI**：没有看板 MCP 时，用本技能目录下的 `scripts/board.mjs`：

  ```bash
  node --use-system-ca <本技能目录>/scripts/board.mjs version
  ```

  - 需要 Node 24 及以上；`--use-system-ca` **每次都要带**，否则 Node 不信任内部证书。仍报证书错误（如 `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`）时，说明本机系统证书库里没有内部根证书，请用户安装，或加上环境变量 `NODE_EXTRA_CA_CERTS=<rootCA.crt 路径>`。
  - 服务地址默认 `https://board.hub.xzs`，可用环境变量 `BOARD_URL` 覆盖。
  - 输出默认是 JSON。出错时错误 JSON 打印到 stderr，退出码不为 0。
- 两者都不可用时停下，告诉用户缺什么：接入看板 MCP（配置方法见 [board 仓库 README「团队成员接入」](https://github.com/xuzhishi/board#团队成员接入)，私有仓库，团队成员可见；也可以找管理员要），或者安装 Node 24 后使用 CLI。
- **版本**：`board_version` 返回 `{version, minClientVersion}`（CLI 的 `version` 另外返回本地的 `clientVersion` 和 `upToDate`）。本技能版本（frontmatter 的 `version`）低于 `minClientVersion` 时，提醒用户从 [`xuzhishi/skills`](https://github.com/xuzhishi/skills) 更新 `outline-board-sync`。CLI 会自动比较并在 stderr 给出提示。

### 2. 身份：本人的 Outline token

看板服务用**调用者本人的 Outline API token** 向 Outline 核实身份和项目权限，不另设账号。看板记下的「同步人」就是这个 token 的主人（`board_whoami` 返回的人），项目页顶部显示「最近同步 @姓名 时间 · 会议」；请求里不另传同步人。token 只从下面两处取得，按顺序检查：

1. **看板 MCP**：已接入时直接用。token 在看板 MCP 配置的 `Authorization` 请求头里；调用 `board_whoami`，返回本人姓名即通过。
2. **CLI + AI 客户端自己的环境变量**：没有看板 MCP 时，CLI 从 AI 客户端自身环境里的 `OUTLINE_API_KEY` 或 `BOARD_TOKEN` 读取 token（`OUTLINE_TOKEN` 也可以）。运行 `node --use-system-ca <本技能目录>/scripts/board.mjs whoami`，返回本人姓名即通过。
3. **两者都没有**：停下来，请用户任选一种方式配置好再重试：
   - 在 AI 客户端的环境变量设置里配置 `OUTLINE_API_KEY`（和 Outline MCP 用的是同一个 token）；
   - 或者接入看板 MCP（配置方法见 [board 仓库 README「团队成员接入」](https://github.com/xuzhishi/board#团队成员接入)，私有仓库，团队成员可见）。

硬性规定：

- **绝不读取其他应用的配置或凭据文件**来找 token，例如 `~/.claude.json`、`~/.codex/config.toml`、Cherry Studio 的配置，即使 Outline MCP 的 token 就存在里面。
- **绝不用 `--token` 传 token**：它会进入命令行、进程列表和对话记录。
- **绝不让用户把 token 贴进对话**，也不要执行带明文 token 的命令（如 `export OUTLINE_API_KEY=…`）。
- 返回 401：token 无效或已过期，请用户在 Outline 设置 → 账号「API 和访问权限」重新创建，并更新客户端里的配置。
- **token 绝不出现在任何输出、文件和 Outline 文档里**，包括同步用的 JSON 文件。

### 3. Outline MCP

读取文档、写回编号、整理目录顺序都要用 Outline MCP（`fetch`、`list_collection_documents`、`update_document`、`move_document`；`list_users` 只在按旧结构同步、匹配纯文本负责人时用）。调用 `list_collections` 确认可用；不可用时停下，告诉用户先接好 Outline MCP（已安装 meeting-to-outline 技能的话，可以按它的环境自检接入）。

## 二、定位项目

1. 从用户给的文档出发（会议纪要、「进度与待办」首页或它的会议子文档、项目根文档都可以；旧结构下也可以是「进度追踪」「待办事项」），用 `fetch` 取得 `collectionId` 和 `parentDocumentId`，再用 `list_collection_documents` 取整棵文档树。
2. 从这篇文档开始**逐级向上**，找到第一个**直接子文档里有「进度与待办」**的节点（新结构）；一直找不到时，改找直接子文档里同时有「进度追踪」和「待办事项」的节点（旧结构）：
   - 找到的是文档：项目就是这篇文档，`rootDocumentId` = 它的 id。
   - 一直找到文档集顶层才出现：项目就是整个文档集，`rootDocumentId` 为空。
   - 例：`示例文档集 › 示例项目 › 进度与待办 › 2026-09-22 示例项目周会` → 项目是「示例项目」这篇文档。
   - 同一个节点下既有「进度与待办」、又有「进度追踪」或「待办事项」（迁移没做完）：停下问用户。
3. 有多个候选层级，或者用户只给了项目名而搜到多个结果时：**列出候选，请用户确认**。
4. **旧结构**（有「进度追踪」「待办事项」，没有「进度与待办」）：先不同步，告诉用户：

   > 「<项目名>」还是旧结构（「进度追踪」「待办事项」）。看板现在只从「进度与待办」首页抽取条目，请先用 outline-promeeting-update 按它的迁移方法（`references/migration.md`）把项目迁移成「进度与待办」，迁移完再同步看板。迁移中的每一次写入都会先给你看。

   用户明确坚持按旧结构同步时，才按 extraction.md 附录执行（§13 是步骤，§1–§12 是规则），并在汇报末尾再提示一次迁移。用户没有坚持就到此为止。
5. 项目名默认取根文档标题（或文档集名）。
6. 用 `board_list_projects`（CLI：`projects`）按 `collectionId` + `rootDocumentId` 查找。已登记就记下项目 `id` 和 `boardUrl`，跳到第四步；没有登记就进入第三步。

## 三、首次：登记项目、「看板」文档、总看板

1. **登记**：`board_register_project`，参数为 `collectionId`、`rootDocumentId`（整个文档集时省略）、`name`（CLI：`register --collection <id> [--root-doc <id>] --name <项目名>`）。这一步是幂等的，重复调用返回同一个项目。返回 403 说明用户对该项目没有编辑权限，请有权限的人来同步。
2. **「看板」文档（征得同意）**：先说明要做什么，得到明确同意后再执行：
   > 将在「<项目名>」下创建一篇名为「看板」的文档（与「进度与待办」同级，排在第一个），正文只有一个嵌入的看板页面。这篇文档由看板服务生成，之后不需要、也不应该编辑。是否创建？

   同意后调用 `board_create_board_doc`（CLI：`board-doc <项目ID>`），这个调用也是幂等的。服务端把「看板」建在项目这一层的第一个（第 0 位）；建好后立即按第十节核对并整理项目目录顺序。报 `template_key_missing` 说明服务端还没配置模板 key：告诉用户请管理员配置，同步照常继续，看板链接一样能用。用户不同意就跳过，在最终汇报里说明以后可以随时说「创建看板文档」。
3. **加入总看板（默认不加入）**：
   > 是否把「<项目名>」加入总看板？总看板对全员只读可见，加入后所有人都能看到本项目的条目。默认不加入。

   只有用户**明确同意**才调用 `board_update_project`，参数 `inOverview: true`（CLI：`project-set <项目ID> --in-overview true`）。项目的 `visibility` 为 `private`（私有文档集）时，要特别说明加入后私有内容会对全员可见。
4. 以后再同步时不重复询问。项目已登记但还没有「看板」文档时，只在汇报里提一句，不追问。

## 四、读取与抽取

1. 用 `fetch` 读取「进度与待办」首页全文，记下返回的 `id` 和 `url`。`list_collection_documents` 的树里，首页下面的子文档就是会议子文档。
2. 用 `board_list_items`，参数 `includeRemoved: true`（CLI：`items <项目ID> --include-removed`），取得看板上现有的全部条目，按编号建立对照。
3. **先核对骨架**（extraction.md §0.1）：正文以「> 以 [标题](链接) 为准」开头（页首另有汇总行和署名行「最近更新 @某人 时间（依据 [标题](链接)）」，旧首页可能没有署名行）；H3「里程碑」「模块」「风险」「缺口」「待办」「最近会议」各一个；五张表的表头逐字是 `| 编号 | 事项 | 负责人 | 截止 | 状态 | 进展 | 关联 |`；没有 H2、其他表格、卡片、段落。不满足就**先停下问用户**，不要按作用去猜表格。
4. **逐行抽取**：五张表的每个数据行是一条条目（某一节只写「无。」就没有条目）：里程碑 → `milestone`，模块 → `module`，风险 → `risk`，缺口、待办 → `task`。每一格按 extraction.md §0.3–§0.8 读取。页首各行（包括署名行）和「最近会议」不是条目。本次关闭、放在表尾的行也照常抽取。
5. **会议子文档和会议纪要不抽取条目**，只在三件事上查阅：定 `sourceMeeting`（§0.9）、给空编号格取号（§0.12）、核对看板上不在首页的编号（§0.13）。
6. **格式不符**：不符合模板的行（extraction.md §0.11：负责人格有多人、状态不是六个词、截止不是规定写法、编号和所在表不一致、关联里有编号以外的文字等）**不推断、不同步**，列进汇报的「格式不符」，请用户改正首页后再同步（或者等下次会后由 outline-promeeting-update 改正）。本技能不替用户改首页。
7. 记下每条条目所在的表和行，第五步写回编号要用。

## 五、编号与写回（只填首页空着的编号格）

本节先定号；写回 Outline 放在第七步，dryRun 自查通过之后执行。这样编号冲突等问题会在改动文档之前暴露出来。

1. **沿用**：首页编号格里已有的编号直接用，永远不改。首页的编号通常已由 outline-promeeting-update 在写入前编好（包括新的模块、里程碑、风险），多数时候本步没有事要做。
2. **编新号**（只给编号格空着的行，细则见 extraction.md §0.12）：
   - 待办和缺口：MMDD 取本次会议（页首第一行）的日期；这一行的进展开头日期早于本次会议时（说明不是本次新增的），先问用户。新号 = max(`board_next_code` 的结果（`type: "task"`，`meetingDate` 为本次会议日期；CLI：`next-code <项目ID> --type task --meeting-date YYYY-MM-DD`）, 首页和全部会议子文档里这一天已用的最大号 + 1)。
   - 模块、里程碑、风险：`type` 设为 `module`、`milestone` 或 `risk`（CLI：`next-code <项目ID> --type module`），同样与首页和全部会议子文档里同类的最大号 + 1 取大。
   - 按首页从上到下的顺序依次分配；用过的号（首页和子文档里出现过的、看板上已有或已移除的）不再使用。
3. **写回位置**：只填首页表格里空着的编号格，没有其他写回位置。**绝不写会议子文档**：它只写一次，本次子文档里缺的编号在汇报里列出，需要时由 outline-promeeting-update 按它的更正流程补上（经用户同意）。
4. **写回方式**：
   - 只用 Outline MCP 的 `update_document`，并且必须用 `editMode: "patch"`。
   - 一次 patch 只改一张表：`findText` 从 `### <表名>` 这一行到这张表的最后一行，从最新的 markdown **原样**复制（包括提及链接、单元格里的空格和分隔行）；`text` 与它逐字相同，只是空着的编号格填上了编号。H3 在首页上只出现一次，第一处匹配就是这张表。
   - 首页第一次 patch 前 `fetch` 一次。patch 成功后，结果里会返回整篇文档的最新 markdown；下一次 patch 的 `findText` 就从这份返回的 markdown 里原样复制，不必再 fetch。只有 patch 找不到匹配或报错时，才重新 `fetch`。
   - 写回之前，用一句话告诉用户要改哪些地方，例如「进度与待办：待办表 2 行补编号 0922-11、0922-12」。写回编号是本技能的固定动作，不需要逐次征求同意。
5. **核对**：用最后一次 patch 返回的 markdown（拿不到时重新 `fetch`）确认编号都已填上、行数没变、提及仍是提及，其他文字一字未改。patch 找不到匹配时，重新读取后再试一次；仍然失败就停下来汇报，**绝不改用 replace、append 或 prepend**。
6. **中断后的恢复**：写回中途失败时，已经写进首页的编号保留不动。下次运行时它们按第 1 条当作已有编号；看板上还没有这些编号，所以 dryRun 时它们出现在 `created` 里。
7. 绝不写：会议纪要、会议子文档、「看板」文档、总看板文档集首页；首页上除空编号格以外的任何文字。

## 六、规范化

逐格规则在 extraction.md §0.3–§0.10，要点：

- **每条都是完整快照**：同步时没填的可选字段会被**清空**。首页的每一行都是完整定义的条目，全部字段按这一行重新生成；首页上已经不写的截止、负责人、关联、完成标准就留空，**不要**从看板现值带过来。只有两个字段沿用看板现值：`sourceMeeting`（看板上已有这个编号时），以及事项里没写 `P0 `、`P1 ` 时的 `priority`。
- **标题**：事项里「；完成＝」前面的文字（去掉开头的 `P0 `、`P1 `）；「完成＝」后面的文字写进描述的 `完成标准：` 一行，保留「（拟）」。
- **状态**：状态格的六个词一一对应——未开始 `not_started`、进行中 `in_progress`、阻塞 `blocked`、待核实 `to_verify`、已完成 `done`、暂停·取消 `paused`。只看状态格，不看进展、不看日期；不是这六个词就是格式不符。
- **截止**：按 extraction.md §0.4 的写法表得到 `due`（`text`、`start`、`end`、`precision`）和 `startDate`；「原 …」写进描述的 `原截止：` 一行，不进 `due.text`；`待定（见 X）`、`无承诺` 没有时间窗。年份取本次会议所在的年份，比会议早三个月以上的算下一年。不要按括号里的原话重新推算日期。
- **负责人**：**只有负责人格里的人进 `owners`**。第一个人 `role` 为 `负责人`，「（执行：…）」里的人为 `执行人`；「待指定（见 X）」时 `owners` 为空，X 进 `relatedCodes`。提及 `@[姓名](mention://…/user/<userId>)` 取姓名和 `userId`；纯文本 `@姓名` 是没有 Outline 账号的人，去掉 @ 只记 `name`，不带 `userId`，也不用 `list_users` 匹配。
- **其他地方的人名**：首页上每一处人名都写成 @，事项（如「完成＝@孙七 签收」）、进展（「（@周八 提出）」「汇报：@李四」）、页首（项目负责人、署名）里的人都**不**进 `owners`。写进看板的文字字段（标题、描述、`statusNote`）之前，提及一律换成纯文本 `@姓名`；「汇报：X」写进描述时只留姓名（extraction.md §0.3、§0.7）。
- **进展**：去掉〔…〕后是 `statusNote`；〔…〕里的录音时间写成描述的 `依据：` 一行。
- **关联**：待办表里第一个 `K` 或 `M` 编号是 `parentCode`；其余编号进 `relatedCodes`（顺序固定，见 §0.8）；「镜像 项目名 编号」→ `mirrorOf`。
- **描述**：固定顺序的几行：`完成标准：…`、`原截止：…`、`依据：…`、`汇报：…`，没有的行省略，不加别的内容。
- **出处**：`source.docUrl`、`source.docId` 是首页（`fetch` 返回的 `url`、`id`），`heading` 是行所在的 H3（里程碑、模块、风险、缺口、待办之一）；不填 `anchor`，由服务端计算。
- **本次会议 `meeting`**：首页页首第一行「以 [标题](链接) 为准」→ `{label: 标题, date: 标题开头的日期, url: 本次会议子文档链接}`。署名行「最近更新 …（依据 [标题](链接)）」只用来核对：「依据」必须链接到同一篇子文档；第一行没有链接时用「依据」的链接；两处不一致时问用户（extraction.md §0.9）。署名行里的人和时间不抽取。
- **来源会议 `sourceMeeting`**（条目首次出现的会议）：看板上已有就沿用；本次新增的就是本次 `meeting`；否则取第一次出现这个编号的会议子文档，没有子文档时取那次会议的纪要（extraction.md §0.9）。同一次会议在 `meeting` 和 `sourceMeeting` 里用完全相同的 label。
- 所有链接都必须以 Outline 地址开头；首页里的相对链接（`/doc/…`）补上首页 `url` 的协议和主机。

## 七、同步与写回（先 dryRun）

1. **组装请求**：

   ```jsonc
   {
     "mode": "incremental",            // 重建时为 "full"
     "meeting": {"label": "2026-09-22 示例项目周会", "date": "2026-09-22", "url": "<本次会议子文档链接>"},
     "items": [ /* 首页五张表的全部条目（格式不符的行除外），格式见 extraction.md §0.10 */ ],
     "removals": []                    // 仅增量模式，见下
   }
   ```

   - **增量**（默认，每次会后）：`items` 放首页的全部条目（格式不符的行除外），未变的条目不会产生变更。看板上有、首页上没有的编号按 extraction.md §0.13 核对：首页和全部会议子文档（含迁移来的原文）里都找不到、并且看板上已经关闭的，放进 `removals`；看板上还没关闭的，列为「关闭未同步」或「疑似漏写」，先问用户，**不要**直接放进 `removals`。
   - **全量重建**（用户说「重建看板」时）：`items` 放首页的全部条目，再加上看板上已有、而且编号在首页（包括格式不符的行）或任何会议子文档里能找到的条目（沿用看板现值，extraction.md §0.14）。不在 `items` 里的条目都会被标记为「已移除」。
2. **dryRun**：MCP 调用 `board_sync`，参数为 `projectId`、上面的字段和 `dryRun: true`。CLI 先把请求写进系统临时目录下的 JSON 文件（**不含 token**），再运行 `sync <项目ID> --file <文件> --dry-run`，也可以用 `--file -` 从标准输入读取。
3. **自查 dryRun 结果**：
   - **看板上还没有的编号都必须出现在 `created` 里**：本次新增的号、本技能补的号、首次同步或上次会后没同步的号。缺了哪个，就查它为什么没进 `items`。
   - **本技能新编的号出现在 `updated` 或 `restored` 里，就是撞号**：它和看板上已有（可能已移除）的同类型条目重了，正式同步会覆盖或复活那条条目。换一个号，重新 dryRun。outline-promeeting-update 编好的号撞号时，不要改首页，停下来告诉用户（由 outline-promeeting-update 按它的更正流程处理）。
   - 已有条目的 `title` 出现在 `updated[].fields` 里：首页上已编号的行标题不再改写，出现这种情况说明编号对错了行或标题被改了，先问用户。
   - `updated[].fields` 的其他字段：每个变化都应能在首页这一行找到原因（例如首页改了截止，`due` 变了；首页去掉了「完成＝」的「（拟）」，`description` 变了），找不到原因就是抽取有误。
   - `warnings` 逐条处理，例如 `parentCode` 或关联编号不存在、时间窗首尾颠倒。能修的修掉，不要为了消除提醒而编造数据。
   - 返回 422 `validation_failed` 时，按 `details` 里的路径修正字段；编号格式与 `type` 不符（如 `K03` 填了 `task`）也是 422，说明这一行放错了表，列为格式不符。409 `code_conflict` 只会出现在服务端的旧数据里，遇到时停下来汇报。
   - **迁移后的第一次同步**（项目刚从「进度追踪」「待办事项」迁移过来）：`removed` 必须为空（有编号出现就是漏迁了条目）；`created` 只有迁移时新编的号和看板上还没有的旧号；`updated` 里会有大量 `source` 变化（出处变成首页，`heading` 变成五个 H3 之一），以及负责人角色、截止时间窗、描述的变化，每一处都应能在首页上找到原因；状态变化只出现在首页确实写了新状态的行；「格式不符」「疑似漏写」应该没有，有的话先请用户修首页。已经从首页删去的旧条目，出处仍指向已归档的「待办事项」或改了名的首页，链接都能打开，不需要处理。
4. **需要用户确认的先确认**：全量模式的 `removed` 列表（编号和标题）；增量模式里「关闭未同步」要补的关闭状态、「疑似漏写」里用户决定移除的编号。都得到确认后才继续。
5. **写回编号**：按第五步的规则，用 patch 把新编号填进首页并核对。任何一处写回失败都先停下，**不要正式同步**，向用户说明哪里没写成功；已写成功的编号按第五步第 6 条在下次运行时处理。
6. **正式同步**：同样的请求去掉 `dryRun`（CLI 去掉 `--dry-run`）。随后可以用 `board_list_changes`（`syncId: "latest"`；CLI：`changes <项目ID> --sync-id latest`）取状态变化的新旧值，供汇报使用。
7. **整理目录顺序**：按第十节核对项目目录的顺序，不对就整理。每次同步都做（本次第三步刚整理过、之后没有新建文档时可以跳过）；正式同步之前就停下的运行不做，下次同步时再整理。

- 新增：0922-01 <标题>、…（超过 10 条只列编号）
- 状态变化：K05 进行中 → 已完成；…
- 其他更新：M03（截止）、…
- 已移除 / 恢复：…

## 九、规则（硬性）

- **绝不修改**会议纪要、会议子文档、「看板」文档、总看板文档集首页。「进度与待办」首页只能往空着的编号格里写编号；旧结构两篇文档的历史部分也不改。
- 写回编号**只用 patch**。新结构只填首页空着的编号格，不改动任何其他文字、格式或结构；旧结构的写回位置见 extraction.md §13.3。
- **只从首页抽取**：会议子文档、会议纪要只查阅。首页不符合模板的行不推断、不同步，列为格式不符；首页骨架不对时先问用户。
- **负责人只看负责人格**：首页上的人名都写成 @，但只有负责人格里的人进 `owners`；纯文本 `@姓名` 不带 `userId`。页首的署名行不抽取，看板的同步人由 token 决定。
- **旧结构先迁移**：项目还是「进度追踪」「待办事项」时先提示用 outline-promeeting-update 迁移；只有用户坚持，才按 extraction.md 附录同步。「进度与待办」与旧文档并存时停下问用户。
- 已有编号永不改动。确实编错时，征得用户同意后用 `board_rename_item`（CLI：`item-rename`）改看板上的编号，首页上的编号由 outline-promeeting-update 同步改正。
- 看板数据以 Outline 为准，状态只由状态格决定。用户想改状态，应该改 Outline 文档，再重新同步。`board_update_item`（CLI：`item-set`）只在用户明确要求临时修正时使用，并提醒用户下次同步会被 Outline 的内容覆盖。
- 不清楚的地方先问用户，包括项目层级、负责人账号、镜像项目、来源会议、编号对应。
- 创建「看板」文档、加入总看板、全量重建时标记移除、增量同步时移除「疑似漏写」的条目或补上「关闭未同步」的状态，都必须先得到用户明确同意。加入总看板默认不加入。
- token 只来自看板 MCP 的配置或 AI 客户端自己的环境变量：不读取其他应用的配置或凭据文件，不用 `--token`，不让用户把 token 贴进对话；不输出、不记录、不写入 token。
- **目录顺序**：项目这一层最上面依次是「看板」「进度与待办」「项目文档」「会议纪要」，其他文档排在后面、彼此的先后不变；缺的跳过，不为了排序新建文档。每次同步后按第十节从上往下逐篇上移整理，并在汇报里写明移动了什么。这是结构调整，不改内容，不需要另外征得同意；移动「看板」文档不算编辑它。只动项目这一层，不调整会议子文档、纪要等下层文档的顺序。
- 不调用 `board_init_overview`。「总看板」文档集由管理员一次性初始化，只有管理员明确要求时才调用。

## 十、项目目录顺序

项目这一层（项目是文档时是它的直接子文档，项目是整个文档集时是文档集顶层的文档）按固定顺序排列，最上面依次是：

1. 看板
2. 进度与待办
3. 项目文档
4. 会议纪要

其他文档排在这四篇后面，彼此的先后保持不变。缺哪篇就跳过哪篇，其余几篇的先后不变；**绝不为了排序新建文档**（「看板」按第三步征得同意后才建，其他几篇由各自的技能按各自的规则创建）。四篇按标题逐字认；同一层有两篇同名的，不整理，在汇报里列出请用户处理。

**何时做**：第三步创建「看板」文档之后立即做一次；每次正式同步之后再做一次（第七步第 7 条）。项目还是旧结构、或者新旧文档并存时不做，迁移完再整理。

**怎么做**（只往上移）：Outline v1.10.0 的 `move_document` 在同一个父级里往上移时，`index` 就是移动后的位置；往下移时 Outline 会先把 `index` 减 1（`documentMover`），容易差一位。所以从上往下逐位整理，每一次都是往上移：

1. `list_collection_documents` 取文档树，找到项目这一层的文档列表。它返回的顺序就是存储的顺序，位置从 0 数起。
2. 定目标顺序：存在的标准文档按上面的顺序排在前面，其他文档按现在的先后跟在后面。
3. 对 i = 0, 1, 2, …（只到最后一篇存在的标准文档为止）：目标顺序里第 i 位的那篇现在不在第 i 位时，调用 `move_document`：`id` 是这篇文档，`index` 是 i；项目是文档时传 `parentDocumentId`＝项目根文档的 id（项目本身那篇文档，不是名为「项目文档」的那篇），项目是整个文档集时传 `collectionId`＝文档集 id（不传 `parentDocumentId`）。前 i 位已经排好，这篇一定在第 i 位之后，所以这是一次往上移，移完正好在第 i 位。标准文档排好后就停：其他文档只是被整体往下挤，彼此的先后没有变，不必移动。
   - 例：现在是「会议纪要、进度与待办、设计稿、看板、项目文档」。i＝0：看板在第 3 位，`index: 0` → 「看板、会议纪要、进度与待办、设计稿、项目文档」；i＝1：进度与待办在第 2 位，`index: 1` → 「看板、进度与待办、会议纪要、设计稿、项目文档」；i＝2：项目文档在第 4 位，`index: 2` → 「看板、进度与待办、项目文档、会议纪要、设计稿」；i＝3：会议纪要已在第 3 位，结束。
4. 移完重新 `list_collection_documents` 核对。仍不对时按第 3 条再做一遍；还不对就停下，在汇报里说明，不要反复尝试。
5. 文档移动时它的子文档跟着走，下层的先后不变。**不调整**会议子文档、会议纪要等下层文档的顺序：它们按各自的规则排（新的在上），由 outline-promeeting-update 和 meeting-to-outline 负责。
6. 整理顺序只改位置，不改任何文档的内容，不需要另外征得同意；移动了哪些文档写进汇报的「目录顺序」一行。
7. 文档集的排序方式不是「手动」时（`fetch` 文档集返回的 `sort.field` 不是 `index`），侧栏按标题排序、看不出位置变化：照样整理存储顺序，在汇报里提醒用户请管理员把文档集改成「手动排序」；不要自行改动文档集的设置（Outline MCP 也改不了）。
