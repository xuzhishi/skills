# 抽取与规范化细则

> 用途：outline-board-sync 第四～七步的操作手册，分两部分：
>
> - **§0「进度与待办」首页（新结构）**：每次同步都用。首页由 outline-promeeting-update 按固定模板（它的 `references/progress-doc-template.md`）整篇重写，每一格都按本节的规则直接读取，不做推断。
> - **附录 §1–§13 旧结构**（「进度追踪」「待办事项」两篇文档，还没迁移的项目）：只在用户坚持不迁移、要求按旧结构同步时使用。§1–§12 的正文与 0.1.0 版相同（只改了 §10 找会议纪要的位置，示例里另一个项目改名为「示例平台」），§13 是原 SKILL.md 里只适用于旧结构的步骤。
>
> 文中的人名、项目、链接、编号和 id 都是虚构的。

## 0. 「进度与待办」首页（新结构）

### 0.1 首页的骨架

项目下有一篇「进度与待办」。它的正文（下称**首页**）是项目的当前全貌；它下面的子文档是每次会议一篇的变化记录，标题 `YYYY-MM-DD 会议主题`（下称**会议子文档**）。首页的骨架是固定的：

```markdown
> 以 [2026-09-15 示例项目周会](<本次会议子文档链接>) 为准 · 纪要：[原文](<会议纪要链接>) · 项目负责人：@周八 · 下次例会：9/22（周二）
>
> 本次延期：M04、K02 · 已过截止未关闭：0908-03 · 待定：K06
>
> 最近更新 @吴九 2026-09-16 10:30（依据 [2026-09-15 示例项目周会](<本次会议子文档链接>)）

### 里程碑

| 编号 | 事项 | 负责人 | 截止 | 状态 | 进展 | 关联 |
|---|---|---|---|---|---|---|
| M02 | 3C 送检；完成＝检测机构出具受理单 | @孙七（执行：@张三） | 9/28–9/29 | 未开始 | 9/15 机构排在 9/28 或 9/29〔06:15–06:40〕 | R01 |

### 模块

（表头同上）

### 风险

（表头同上）

### 缺口

（表头同上）

### 待办

（表头同上）

### 最近会议

- [2026-09-15 示例项目周会](<本次会议子文档链接>)
```

同步前先核对骨架。下面任何一条不满足，就**停下问用户**，不要按作用去猜表格：

- 正文以「> 以 [标题](链接) 为准」开头。页首引用块里另外两行是汇总和署名（「最近更新 @某人 时间（依据 [标题](链接)）」）；署名行是后来加的，旧首页没有它不算骨架问题。
- H3「里程碑」「模块」「风险」「缺口」「待办」「最近会议」各出现一次，顺序如上。
- 五张表的表头逐字是 `| 编号 | 事项 | 负责人 | 截止 | 状态 | 进展 | 关联 |`（分隔行的写法不限）。某一节下面只写「无。」时，这一节没有条目。
- 没有 H2、`---`、其他表格、卡片、段落。

骨架没问题、只是个别行不合规时，不停下：这些行按 §0.11 列为「格式不符」，其余的照常同步。

### 0.2 条目来源

| 首页位置 | 条目 | `type` | 编号格式 |
| --- | --- | --- | --- |
| 「里程碑」表的每个数据行 | 里程碑 | `milestone` | `M01`（M 加至少两位数字） |
| 「模块」表的每个数据行 | 模块 | `module` | `K01` |
| 「风险」表的每个数据行 | 风险 | `risk` | `R01` |
| 「缺口」表的每个数据行 | 缺口（正式的待办） | `task` | `MMDD-NN` |
| 「待办」表的每个数据行 | 待办 | `task` | `MMDD-NN` |

- **不是条目**：页首各行（第二行是方便扫读的汇总，第三行是署名）、「最近会议」清单、会议子文档、会议纪要。会议子文档只在三件事上查阅：定 `sourceMeeting`（§0.9）、给空编号格取号（§0.12）、核对看板上不在首页的编号（§0.13）。
- 本次关闭的行（状态是已完成或暂停·取消，放在各表表尾）也是条目，照常同步：看板正是从这一行收到关闭状态的。下一次重写时它们会从首页删去，这不是删除条目（§0.13）。

### 0.3 逐格对照

一行从左到右读，每一格都有固定的去处：

| 格 | 字段 | 规则 |
| --- | --- | --- |
| （行所在的 H3） | `type`、`source.heading` | §0.2、§0.9 |
| 编号 | `code` | 照抄。和所在表的编号格式对不上（如「待办」表里写了 `K03`）→ 格式不符。空着 → §0.12 |
| 事项 | `title`、`priority`、描述的 `完成标准：` 行 | 在第一个「；完成＝」处切开：前面是标题部分，后面是完成标准（保留「（拟）」）；没有「；完成＝」时整格都是标题部分。标题部分以 `P` 加数字加空格开头（如 `P0 `）时，这个标记是 `priority`，其余是 `title`；没有标记时 `priority` 沿用看板现值（新条目为 `null`） |
| 负责人 | `owners`；`relatedCodes` | §0.5 |
| 截止 | `due`、`startDate`；描述的 `原截止：` 行；`relatedCodes` | §0.4 |
| 状态 | `status` | §0.6 |
| 进展 | `statusNote`；描述的 `依据：`、`汇报：` 行 | §0.7 |
| 关联 | `parentCode`、`relatedCodes`、`mirrorOf` | §0.8 |

「；」「＝」「（」「）」「：」写成半角的也认。

**人名**：首页上每一处人名都写成 @（outline-promeeting-update 的规定）：有 Outline 账号的是提及 `@[姓名](mention://…)`，没有账号的是纯文本 `@姓名`。人名可能出现在任何一格和页首，但**只有负责人格里的人进 `owners`**（§0.5）。其他地方的人名——事项里的「完成＝@孙七 签收」、进展里的「（@周八 提出）」「汇报：@李四」、页首的项目负责人和署名——都不进 `owners`，也不查 `userId`。

写进看板的文字字段（`title`、描述的各行、`statusNote`、`due.text`）之前，先把其中的提及 `@[姓名](mention://…)` 换成纯文本 `@姓名`（去掉链接，保留 @ 和方括号里的姓名）；纯文本 `@姓名` 原样保留。这样同一行每次同步都得到相同的文字，不随提及 id 变化，看板页面上也不会出现链接代码。

### 0.4 截止 → `due`、`startDate`

截止格只有 8 种写法（outline-promeeting-update 模板的规定）。按四步读取：

1. **开始日期**：以 `<日期>起→` 开头时，这个日期写进 `startDate`，去掉这个前缀再往下读。没有这个前缀时 `startDate` 为 `null`。
2. **原日期**：末尾括号里以「原 」开头的那一段（和括号里其他文字用「；」隔开）是改期前的日期：把「原 」后面的文字写成描述的 `原截止：…` 一行，并从截止里去掉这一段；去掉后括号空了，就连括号一起去掉。如 `11/10（原 10/31）` → `11/10`，`原截止：10/31`。
3. **`due.text`**：剩下的文字原样写进 `due.text`（不超过 100 字）。
4. **时间窗**：剩下的文字按下表从上往下匹配，取第一条符合的；一条都不符合 → 格式不符。

| 剩下的写法 | `start` | `end` | `precision` | 另外 |
| --- | --- | --- | --- | --- |
| `待定（见 X）` | `null` | `null` | `null` | X 加入 `relatedCodes` |
| `无承诺` | `null` | `null` | `null` | |
| `约D` 或 `约D（算式）` | D 前 3 天 | D 后 3 天 | `fuzzy` | 括号里出现的编号加入 `relatedCodes` |
| `D1–D2` 或 `D1–D2（原话）` | D1 | D2 | 首尾含起来不超过 3 天记 `day`，更长记 `fuzzy` | |
| `D` 或 `D（原话）` | 按原话的类别（下表） | D | 按原话的类别 | |

- D 是 `M/D`，跨年时是 `YYYY/M/D`。`M/D` 的年份取本次会议（页首第一行）所在的年份；这样得到的日期比会议早三个月以上时，算下一年。只看本次会议的日期，不看同步当天。
- 区间号写 `–`；写成 `-`、`~`、`至` 的也按区间读。
- **不要按原话重新推算日期**：D 就是截止，原话只决定精度和 `start`。

**原话的类别**（原话＝括号里去掉「原 …」那一段之后剩下的文字），从上往下取第一条符合的：

| 原话 | `precision` | `start` |
| --- | --- | --- |
| 含「上旬」「月初」/「中旬」「月中」/「下旬」「月底」 | `xun` | D 所在月的 1 日 / 11 日 / 21 日 |
| 就是「X月」「X月内」「下月」 | `month` | D 所在月的 1 日 |
| 就是「本周」「本周内」「下周」「下下周」，或者以「节前」或节日名加「前」结尾（元旦、春节、清明、五一、劳动节、端午、中秋、国庆） | `week` | D 前 6 天 |
| 其他（具体日期、明天、周X、下周三前、下次例会……），或者没有括号 | `day` | 与 D 相同 |

### 0.5 负责人 → `owners`

负责人格只有两种写法：

| 写法 | `owners` |
| --- | --- |
| `<人>` 或 `<人>（执行：<人>、<人>…）` | 第一个人，`role: "负责人"`；「执行」里的人依次在后，`role: "执行人"` |
| `待指定（见 X）` | `[]`；X 加入 `relatedCodes` |

`<人>` 是下面两种之一：

- **提及** `@[姓名](mention://<提及id>/user/<userId>)`，或两段写法 `@[姓名](mention://user/<userId>)`：`name` 取方括号里的姓名，`userId` 取 `/user/` 后面那段 UUID（第一段的提及 id 每次都不同，不要用）。
- **纯文本** `@姓名`（没有 Outline 账号的人）：去掉 `@`，`name` 取 `@` 后面到「（」「、」或格末为止的文字（去掉首尾空白），**不带 `userId`**，也不用 `list_users` 去匹配。首页上有账号的人一律写成提及，纯文本 `@姓名` 就是写入前已经向用户确认过、没有账号的人（外部人员等）。

规则：

- 同一个 userId（没有账号时同一个姓名）只记一次，保留第一次出现的位置；最多 20 人。
- 汇报人不在负责人格里，不进 `owners`（§0.7）。
- 以下都是格式不符：括号外不止一个人（`@张三、@李四`、`@张三 @李四`）；人名前没有 `@`；「发言人3」这类匿名标签；「待指定」后面没有「（见 编号）」。

### 0.6 状态 → `status`

| 状态格 | `status` |
| --- | --- |
| 未开始 | `not_started` |
| 进行中 | `in_progress` |
| 阻塞 | `blocked` |
| 待核实 | `to_verify` |
| 已完成 | `done` |
| 暂停·取消 | `paused` |

- 状态格去掉首尾空白后必须正好是这六个词之一（「暂停·取消」中间的点写成 `・`、`•` 也认）；否则这一行格式不符，**不做推断**：不看进展、不看表情、不按附录 §6 去猜。
- 只看状态格：截止过了不改判，进展里写了什么也不改判。逾期由页面按 `due.end` 自动标出。

### 0.7 进展 → `statusNote`、描述

进展格的写法是 `M/D <事实>[；标签：…]〔mm:ss–mm:ss〕`，前面可能有「未提及（N）：」「逾期未汇报（N）：」前缀。

- **`statusNote`**：去掉所有〔…〕（连同紧挨在它前面的空格）后的文字，提及换成纯文本 `@姓名`（§0.3），去掉首尾空白；前缀和各种标签原样保留。空着时为 `null`；超过 500 字 → 格式不符。
- **描述的 `依据：` 行**：各个〔…〕里的文字按出现顺序用「、」连起来，如 `依据：06:15–06:40`、`依据：用户 9/16 确认`。没有〔…〕就没有这一行。
- **描述的 `汇报：` 行**：进展里有「汇报：X」时，X 取到「；」「〔」或格末为止，只留姓名（提及取方括号里的姓名，纯文本 `@姓名` 去掉 @），写成 `汇报：X`，如 `汇报：@[李四](mention://…)` → `汇报：李四`。汇报人**不**进 `owners`。
- 「外部：」「卡点：」「下一步：」等其他标签只留在 `statusNote` 里；进展里提到的编号也不加入 `relatedCodes`，提到的人也不进 `owners`。

### 0.8 关联 → `parentCode`、`relatedCodes`、`mirrorOf`

关联格按「、」切开，每一段必须是一个编号（`MMDD-NN`、`K01`、`M01`、`R01`），或者 `镜像 <项目名> <编号>`；出现别的文字 → 格式不符。空着就是没有关联。模板不在关联里写人；万一某一段是人名（提及或 `@姓名`），跳过这一段：不进 `owners`、不进 `relatedCodes`，也不算格式不符。

- **`parentCode`**：只有「待办」表的行才有，取关联格里**第一个** `K` 或 `M` 编号。「缺口」表和里程碑、模块、风险表都不填 `parentCode`。
- **`relatedCodes`**：按「负责人格里的 X（待指定）→ 截止格里的编号（待定的 X、`约` 括号里的编号）→ 关联格里的编号」的顺序收集，去重，再去掉本行自己的编号和 `parentCode`。顺序固定，同一个首页每次都得到相同的结果（看板按顺序比较，顺序一变就算一次更新）。
- **`mirrorOf`**：`镜像 <项目名> <编号>` → `{"projectId": …, "code": <编号>}`，`projectId` 用 `board_list_projects` 按项目名精确匹配。一行最多一个镜像段，多了 → 格式不符。
  - 镜像行在首页上有自己完整的一行（标题、负责人、截止、状态），照常按本节生成全部字段，另外带上 `mirrorOf`；页面会显示原条目的实时状态，并标注「来自 <项目名>」。
  - 项目名对不上、有多个同名项目，或者对方项目还没在看板登记：不填 `mirrorOf`，这一行照常作为本项目的普通条目同步，列进「待确认」。
  - 服务端返回 422「镜像来源项目不存在，或你在 Outline 中没有该项目的读取权限」：去掉这一行的 `mirrorOf` 重新 dryRun，不要换写法重试，列进「待确认」。
  - 镜像段里的编号属于对方项目，不加入本项目的 `relatedCodes`。

### 0.9 出处、本次会议、来源会议

- **`source`**：`{"docUrl": 首页 fetch 返回的 url, "docId": 首页的 id, "heading": 行所在的 H3}`，`heading` 是「里程碑」「模块」「风险」「缺口」「待办」之一。不填 `anchor`：每个 H3 在首页上只出现一次，服务端按标题算出的锚点每次都一样。
- **本次会议 `meeting`**（请求顶层）：页首第一行「以 [标题](链接) 为准」→ `{"label": 链接文字, "date": 标题开头的 YYYY-MM-DD, "url": 链接}`，链接指向本次会议的子文档。第一行后面可能还有「（模板迁移 M/D）」之类的说明，不影响读取。
  - 署名行「最近更新 @某人 时间（依据 [标题](链接)）」只用「依据」的链接：它必须和第一行指向同一篇子文档（比较链接末尾的 urlId）。第一行没有链接时，用「依据」的链接和文字；两处都有、却指向不同的文档时，问用户。
  - 两处都没有链接时，问用户。
  - 署名行里的人和时间不抽取：看板上的同步人由服务端按调用者的 token 记录（`board_whoami` 返回的人），页面顶部显示「最近同步 @姓名 时间 · 会议」，请求里不另传同步人。
- **链接**：所有链接都必须以团队的 Outline 地址（`https://outline.hub.xzs`）开头，否则会被拒绝。首页里的站内链接可能是相对路径（`/doc/…`），这时补上首页 `url` 的协议和主机。本文示例里的 `https://outline.example` 只是占位。

**`sourceMeeting`**（条目**首次出现**的会议），从上往下取第一条符合的：

1. **看板上已经有这个编号**（包括已移除的）：沿用看板现值，不改（迁移前指向会议纪要的，保持不变）。
2. **本次新增的编号**（本次子文档的「本次变化」里有它的「新增」行，或者是本次由 §0.12 补的编号）：本次的 `meeting`。
3. **看板上还没有、编号出现得更早**（例如首次同步、迁移后第一次同步、上次会后没同步）：在会议子文档里找**第一次**出现这个编号的那一篇（「新增」行，或迁移来的原文），填 `{"label": 子文档标题, "date": 标题开头的日期, "url": 子文档链接}`。
   - 子文档的先后按标题排：先按日期；同一天的几篇，不带时间的在前，带「 HH:MM」的按时间排在后面。
   - 待办和缺口：先看编号里 MMDD 那一天的子文档，正文里有这个编号就是它。
   - 模块、里程碑、风险：从最早的子文档往后读，第一篇正文里出现这个编号（前后不是数字或字母）的就是。
4. **找不到子文档**：用那次会议的纪要，即「会议纪要」下标题以该日期开头的文档（旧的两级结构下是「会议纪要/YYYY-MM-DD」目录里的纪要），`label` 用纪要标题（`YYYY-MM-DD 会议主题`，可能带「 HH:MM」，原样照抄）；旧标题 `HH:MM-HH:MM 主题` 去掉开头的时间段，前面加上日期目录的日期和一个空格，写成 `YYYY-MM-DD 主题`（与 outline-promeeting-update 给这场会建子文档时用的标题相同）。
5. **都没有**：只填 `label` 和 `date`，列进「待确认」。

- 同一次会议在 `meeting` 和各条目的 `sourceMeeting` 里用**完全相同**的 label。会议子文档的标题与纪要标题逐字相同，两处自然一致。
- 看板上某次会议已有的 label 与子文档标题不一致（例如迁移前用了别的会议名）时，不改看板上的值，在汇报里说明。
- 一条条目**最近一次**在哪次会议上变化，不写进 `sourceMeeting`：进展开头的 `M/D` 就是那次会议，同一日期的会议子文档记着改了什么；看板变化条上的会议链接也指向本次子文档。

### 0.10 组装条目

每一行生成一条完整的条目，只能有下面这些键，多出任何键都会被拒绝（422）：

```jsonc
{
  "code": "K02", "type": "module", "title": "…",
  "description": "完成标准：…\n原截止：…\n依据：…\n汇报：…",  // 固定顺序，没有的行省略；一行都没有时为 null
  "status": "blocked", "statusNote": "…",
  "due": {"text": "…", "start": "YYYY-MM-DD", "end": "YYYY-MM-DD", "precision": "fuzzy"},
  "startDate": null,
  "owners": [{"name": "赵六", "userId": "…", "role": "负责人"}],
  "priority": null,
  "parentCode": null,
  "relatedCodes": [],
  "source": {"docUrl": "…", "docId": "…", "heading": "模块"},
  "sourceMeeting": {"label": "…", "date": "…", "url": "…"},
  "mirrorOf": null
}
```

- **描述**只由四种行组成，顺序固定：`完成标准：`（§0.3）、`原截止：`（§0.4）、`依据：`（§0.7）、`汇报：`（§0.7）。不加别的说明，也不把看板上原有的描述带过来。顺序固定，同一个首页每次都得到相同的描述，不会产生多余的「更新」。
- **所有行都是完整定义的条目**（附录 §5.2）：字段全部按这一行重新生成。首页上已经不写的截止、负责人、关联、完成标准，就是 `null` 或空，**不要**从看板现值带过来。只有两个字段沿用看板现值：`sourceMeeting`（§0.9 第 1 条），以及事项里没写 `P0 `、`P1 ` 时的 `priority`。
- 同一次同步里编号不能重复，也不能同时出现在 `items` 和 `removals` 里。

### 0.11 格式不符

下面任何一条成立，这一行就是「格式不符」：**不推断、不同步**（不放进 `items`），列进汇报的「格式不符」，写明编号（没有编号时写表名和第几行）和原因。请用户改正首页后再同步，或者等下次会后由 outline-promeeting-update 改正。本技能不替用户改首页。

| 格 | 格式不符的情况 |
| --- | --- |
| 编号 | 和所在表的编号格式对不上（H3 与编号前缀不一致）；同一个编号在首页上出现在不止一行（这几行都算） |
| 事项 | `title` 超过 200 字 |
| 负责人 | 不是 §0.5 的两种写法 |
| 截止 | 不是 §0.4 的写法，包括空着 |
| 状态 | 不是六个词之一 |
| 进展 | 去掉〔…〕后超过 500 字 |
| 关联 | 有编号和「镜像 项目名 编号」以外的文字；镜像段不止一个 |

- 格式不符的行，编号仍然算「在首页上」：§0.13 不会把它列为疑似漏写，也不会移除它。
- 增量同步时，看板上这条保持原样；全量重建时，看板上已有的格式不符条目按看板现值放进 `items`（§0.14），免得被标记为已移除。
- 里程碑、模块、风险缺「完成＝」不算格式不符，照常同步，在「待确认」里提一句。
- 整个首页的骨架有问题（§0.1）时，不逐行处理，停下问用户。

### 0.12 编号：只填首页空着的编号格

首页的编号由 outline-promeeting-update 在写入前编好（包括新的模块、里程碑、风险），一般没有空的编号格。只有漏编的行才需要本技能编号：

1. **定号**：
   - 待办和缺口：MMDD 取本次会议（页首第一行）的日期。这一行进展开头的日期（去掉「未提及（N）：」这类前缀后）早于本次会议，说明它不是本次新增的，先问用户。新号 = max（`board_next_code`，`type: "task"`、`meetingDate` 为本次会议日期，返回的号；首页和全部会议子文档里这一天已用的最大号 + 1）。待办和缺口共用一个序列。
   - 模块、里程碑、风险：新号 = max（`board_next_code`，`type` 为 `module`、`milestone` 或 `risk`，返回的号；首页和全部会议子文档里同类的最大号 + 1）。
   - 几行都空着时，按首页从上到下的顺序（里程碑、模块、风险、缺口、待办，表内按行序）依次分配。
   - 用过的号都不再使用：首页和子文档里出现过的，看板上已有或已移除的。
2. **写回位置**：只填首页表格里空着的编号格，没有其他写回位置。会议子文档只写一次，本技能**绝不修改**；本次子文档里这些行缺的编号，在汇报里列出，需要时由 outline-promeeting-update 按它的更正流程补上（要经用户同意）。
3. **patch 的写法**：一次 patch 只改一张表。`findText` 从 `### <表名>` 这一行开始，到这张表的最后一行为止，从最新的 markdown 里**原样**复制（包括提及链接、单元格里的空格和分隔行）；`text` 与它逐字相同，只是空着的编号格填上了编号。H3 在首页上只出现一次，第一处匹配就是这张表。

   ```markdown
   写回前：|  | 整理 3C 送检警示语清单 | @孙七 | 9/22（下次例会） | 未开始 | 9/15 新增〔21:40–22:00〕 | M02 |
   写回后：| 0915-11 | 整理 3C 送检警示语清单 | @孙七 | 9/22（下次例会） | 未开始 | 9/15 新增〔21:40–22:00〕 | M02 |
   ```

   空编号格里的空格以 `fetch` 结果为准，只在格里填上编号，别的不动。
4. 文本没有任何变化的 patch 会被 Outline 当作错误返回，不要重复提交已经写好的编号。
5. 写完核对：编号齐全、行数不变、提及仍是提及、其他文字一字未改。第一次给首页写回后，提醒用户打开 Outline 看一眼表格是否正常。

### 0.13 看板上不在首页的编号

首页只有当前全貌，上一版关闭的行这一版已经删去，所以「看板上有、首页上没有」通常是正常的。用 `board_list_items`（`includeRemoved: true`）的结果，逐个核对看板上**没被移除**、编号又不在首页上（格式不符的行也算在首页上）的条目：

1. 在全部会议子文档里查这个编号：它有没有在任何子文档（包括迁移来的原文）的正文里出现过；从新到旧，第一篇在「本次变化」表里记了它的「关闭」或「恢复」行的子文档记的是哪一种。
2. 按下表处理：

| 看板上的状态 | 子文档里 | 处理 |
| --- | --- | --- |
| 已关闭（`done`、`paused`） | 出现过 | 正常，不处理 |
| 已关闭 | 首页和子文档里都找不到 | 放进 `removals` |
| 没关闭 | 最近一次记的是「关闭」 | **关闭未同步**：关闭那次会后没做看板同步，看板没收到关闭状态。列进「待确认」，用户同意后按下面的方法补上 |
| 没关闭 | 出现过，但没记「关闭」，或者最近一次记的是「恢复」 | **疑似漏写**：首页漏了这一行。列进「待确认」，不放进 `removals`；请用户决定是补回首页（由 outline-promeeting-update 更正），还是确认它已经关闭 |
| 没关闭 | 首页和子文档里都找不到 | **疑似漏写（文档里找不到）**：列进「待确认」；用户确认这条确实不要了，才放进 `removals` |

- **补上关闭状态**：以 `board_list_items` 里这条条目为底稿，删掉 `id`、`projectId`、`removed`、`createdAt`、`updatedAt` 和 `source.url`，只改 `status`（关闭行「→」后面的词按 §0.6 对应）和 `statusNote`（写成 `M/D 关闭：<关闭行「变化」格的文字>`，M/D 是那篇子文档的日期），其余字段原样保留，放进 `items`。
- 子文档多时，先把全部子文档读一遍，记下每个编号出现在哪几篇、哪篇记了「关闭」「恢复」，之后的核对和取号（§0.12）都查这份记录。

### 0.14 全量重建

用户说「重建看板」时，`items` 放：

1. 首页上所有不是格式不符的行，按本节生成；
2. 看板上已有、而且编号在首页上（格式不符的行）或任何会议子文档里能找到的条目：以看板现值为底稿（删掉 `id`、`projectId`、`removed`、`createdAt`、`updatedAt` 和 `source.url`），原样放入。

不在 `items` 里的条目都会被标记为「已移除」，所以 dryRun 的 `removed` 列表要先给用户看，得到确认后才正式同步。

## 1. 当前部分与历史部分（旧结构）

outline-promeeting-update 更新文档时，会把最新状态写在文档**开头的当前部分**，旧内容保留在后面的**历史部分**。

| 判断依据 | 当前部分 | 历史部分 |
| --- | --- | --- |
| 典型标题 | 「当前进展（以2026-09-22会议为准）」「当前待办（2026-09-22会议）」「当前里程碑」；也可能只有一个「★ 2026-09-16 补充待办/更新」 | 「历史依据」「历史待办原文」「2026-09-10 历史基线」「9月1日历史基线」「原有待办」 |
| 位置 | 文档开头，直到**分界线**为止 | 分界线之后的所有内容 |
| 本技能的处理 | 抽取条目，写回编号 | 只读：可以查阅，例如查某个沿用编号条目的原始表述；不抽取，不写入 |

**分界线**是第一条**后面紧跟着历史标题**的 `---`。历史标题指：

- 含「历史」「原有」「基线」「原文」「保留原文」的标题，如「历史依据（以下保留原文）」「历史待办原文」「9月1日历史基线」「原有待办」；
- 或者是比当前部分**更早的会议日期**的标题，如当前部分以 9/22 会议为准时的 `## ★ 2026-09-16 会后更新`、`## 2026-09-10 …`。

注意：

- 当前部分内部的 `---` 不是分界线。例如「当前待办」里的卡片之间常用 `---` 隔开，这些 `---` 后面紧跟的是下一张卡片（`### …`），不是历史标题。
- 分界线之前的「★ YYYY-MM-DD …」小节属于当前部分，即使没有「当前…」标题（例如整个当前部分就是 `## ★ 2026-09-16 补充待办/更新`）。
- 整篇文档没有当前 / 历史之分（例如只经历过一次会议）时，整篇都算当前部分。
- 判断不了边界时，问用户。
- 当前部分里的说明文字不是条目，例如「★ … 会议更新」引用块、「人员按本场确认：…」段落、表格后的补充说明、卡片区开头的「以下是对…的细化」。

真实文档常见的样子：

```markdown
## 当前待办（2026-09-22会议）

以下是对原始待办及既有任务的细化，按主题关联执行，不表示重复新建同一任务。

### 移动端适配
…
---
### 用户试用反馈        ← 仍是当前部分：这条 --- 后面是卡片
…
---
## 历史待办原文（以下保留）   ← 分界线：这条 --- 后面是历史标题
```

### 2.1 按作用识别表格和风险

promeeting-update 在不同会议里写出的当前部分结构不完全一样，例如「新增里程碑」（时间 | 交付内容 | 责任人 / 状态）、「模块/任务增量状态」（模块/任务 | 责任人 | 状态 | 本次结论与依赖）、「里程碑」（时间 | 里程碑）、「模块进度」（模块 | 状态 | 说明）、「模块开发看板」（… | 优先级 | 状态 | 关键节点）。先按**作用**认出表格，再按列的**含义**取值。

| 作用 | 怎么认 | 条目类型 |
| --- | --- | --- |
| 里程碑 | 标题含「里程碑」「时间节点」；或第一列是时间、另一列是交付内容 | milestone |
| 模块 | 标题含「模块」（「模块与任务状态」「模块进度」「模块开发看板」「模块/任务增量状态」等）；第一列是模块或事项名 | module |
| 待办 | 待办事项里带编号列、或标题含「待办」的表 | task |

列与字段的对应（列名不必完全一样，按含义对应）：

| 列（举例） | 字段 |
| --- | --- |
| 交付或动作、交付内容、里程碑、模块、模块/事项、模块/任务、待办内容 | `title` |
| 时间、时间/条件、节点、关键节点、截止 | `due`（§7） |
| 责任人、负责人 | `owners`，`role` 为「负责人」 |
| 执行人 | `owners`，`role` 为「执行人」 |
| 相关发言人/执行人 | `owners`，`role` 见 §8 |
| 状态、状态与边界、当前状态与执行边界、时间/状态核对 | `status`（§6）、`statusNote` |
| 优先级（P0/P1…） | `priority` |
| 「责任人 / 状态」这类合并列 | 按「；」拆开：前半是负责人，后半是状态 |
| 说明、依据、本次结论与依赖等其余列 | `description`，每列一行并加列名，如 `依据：03:10–04:02` |

- 表格对不上任何作用，或者某列不知道该对应什么字段时，先问用户，不要猜。
- 风险可能写成引用块（`> ⚠️ **名称：** 描述`），也可能写成列表（`* ⚠️ **名称：** 描述`，或不加粗的 `- ⚠️ 名称：描述`）。都按 §3.3 抽取：名称取加粗部分；没有加粗时取第一个冒号（`：` 或 `:`）前的文字，去掉 `⚠️`。写回位置见 §9.3。

### 2.2 卡片、模块与原始待办：同一件事只留一条

待办事项当前部分的卡片常常只是把进度追踪里的某个模块、或某条已编号的待办再写一遍。真实文档在卡片区开头就会写明「以下是对原始待办及既有任务的细化……不表示重复新建同一任务」。如果每张卡片都建一条待办，同一件事会在看板上出现三四次。所以逐张卡片按下面的顺序判断，取第一条符合的：

0. **标题里已经有 `[编号]`**（以前同步过）：沿用这个编号，照旧作为待办（§4.3），不再重新判断。
1. **与模块同名 → 由模块覆盖**：卡片标题（去掉首尾空白）与进度追踪模块表某一行的「模块/事项」列**完全相同**。
   - 不建条目，不在卡片标题写编号。
   - 卡片的 `**相对旧记录的变化：**` 追加到该模块的 `description`（一行 `相对旧记录的变化：…`）。卡片正文与模块行的状态列不一样时，把卡片正文也追加进去（一行 `待办卡片：…`）。
   - 在汇报里列一次：「由模块覆盖、未单独建待办：<卡片标题> → K05、…」。
2. **复述已有待办 → 并入那条**：只在文档写明卡片「不表示重复新建同一任务」（或意思相同的说明）时适用。卡片说的就是某条已有待办：本次会议已编号的原始待办（如 `0922-04`），或「原任务状态更新」表里的旧待办。判断依据是卡片文字写出了那条待办的编号，或者卡片标题和正文说的是同一个动作。
   - 不建条目，不写编号；卡片里的新信息（新的时间、状态变化）追加到那条待办的 `description`（一行 `待办卡片：…`）。那条待办以看板现值为底稿时（§5.2 部分信息的条目），底稿里已有的 `待办卡片：` 行要替换成这次的内容，不要重复追加。
   - 可能对应不止一条、或者只是主题相近时，先问用户。用户没有答复时，这张卡片**不建条目、不写编号**，列进汇报的「待确认」。
3. **其余卡片 → 新待办**：没有对应模块、也没有对应已有待办的卡片才成为 task，编本次会议的下一个号（`0922-10`…），标题前写 `[编号]`，字段见 §4.3。

没有「不表示重复新建」这类说明时，第 0、1、3 条照样适用，第 2 条不适用：与模块同名的卡片仍由模块覆盖，其余卡片都成为待办。

| `title` | 风险名，去掉冒号，如「接口联调排期」（取法见 §2.1） |
| `description` | 冒号后面的描述原文 |
| `status` | 仍在跟踪的风险用 `in_progress`；已经发生并卡住工作的用 `blocked`；文档写明已解除的用 `done`；不再相关的用 `paused` |
| `statusNote` | 文中有状态表述时填写，否则留空 |
| `relatedCodes` | 风险涉及的里程碑、模块、待办的编号，如 `["M06", "K07"]`。描述里写出了编号，或者写出的事项名与某个模块、里程碑的标题完全相同时才填；对不上就不填 |

## 4. 待办事项（旧结构）

### 4.1 带编号列的待办表

| 字段 | 取值 |
| --- | --- |
| `code` | 编号列 |
| `title` | 待办内容原文，去掉其中的 @提及和末尾句号。超过 200 字时截取主干，全文放进 `description` |
| `owners` | 内容里的 @提及（promeeting-update 用它标注责任人，`role` 填「负责人」），以及责任人列（`role` 填「负责人」） |
| `due` | 内容里或「时间/状态核对」列中的时间表述，按 §7 推算，例如「明天」「本周内」「中秋节前」 |
| `status` / `statusNote` | 状态列或「时间/状态核对」列的原文，按 §6 判断 |
| `description` | 其他列，加上列名 |

### 4.2 「原任务状态更新（沿用原编号）」表

这张表更新的是以前会议的待办。第一列「原编号/任务」形如 `0916-01 找外包团队及开发周期`，也可能没有编号，如 `9/10 日志归档方案`，甚至连日期都没有，如 `上线前用户试用`。第一列通常只是简称，完整的待办写在历史部分那次会议的原文里。

按下面三种情况处理：

1. **有编号，看板上已有这个编号**（部分信息的条目，§5.2）：以看板现值为底稿，只更新 `status`、`statusNote`、`source`，文档给出新时间时再更新 `due`。标题、负责人、描述、来源会议都沿用看板现值。
2. **有编号，但看板上没有**（首次同步，或者上次写回后没来得及同步）：到历史部分找这个编号**定义**的那一行（例如「★ 2026-09-16 会议待办」表里的 `0916-01`，只读），从那里取完整的条目：
   - `title`：那一行的待办内容原文，去掉 @提及和末尾句号（不要用本表第一列的简称）
   - `owners`：那一行的 @提及和责任人列，`role` 填「负责人」
   - `description`：那一行的其他列，加上列名
   - `due`：那一行的时间表述，**以原会议日期为基准**按 §7 推算，如 9/16 会议里的「周五前反馈」→ 9/18
   - `sourceMeeting`：原会议（§10）

   再用本表这一行覆盖 `status`、`statusNote`（和新时间，见下）。历史部分也找不到这个编号时，问用户。
3. **没有编号的旧待办**：先在历史部分找到对应的旧待办，按**位置**补编号（§9.1），然后像第 2 种情况一样从历史原文建条目。
   - 行里写了会议日期（`9/10 日志归档方案`）：在那次会议的待办列表里找；9/10 待办列表里的第 1 条 → `0910-01`。
   - 行里既没有编号也没有日期：在历史部分所有会议的待办里找。
   - 可能对应不止一条旧待办时（例如「上线前用户试用」既像 9/10 待办第 4 条「推进上线前的验证」，又像 9/16 未编号清单里的「组织内部试用」），**列出候选请用户选**；一条都对不上时也问用户。
   - 一行对应多条旧待办（如 `9/10 接口文档更新、招聘`）：拆成多条条目，各自按位置编号，写回时单元格开头写 `0910-02、0910-03 `。

三种情况共用的规则：

- `statusNote` 写成「最新状态；尚待完成：…」，不超过 500 字。
- **新的时间**：「最新状态」「尚待完成」里给出了新的时间安排（如「改为国庆节后」「延到10月底」）时，用新的原文和按本次会议日期推算的时间窗替换 `due`；推算不出窗口时只写 `due.text`，`start`/`end`/`precision` 为 `null`。原来的截止写进 `description` 末尾一行 `原截止：<原 due.text>`（已有这一行就不再加）。没有给出新时间时 `due` 不变。

### 4.3 卡片式小节

只有按 §2.2 判定为新待办（或标题里已有 `[编号]`）的卡片才按本节建条目。

```markdown
### 用户试用反馈

内部5人试用已完成，多数场景可用；弱网环境下同步仍慢。交互细节还在调整，计划中秋前请客户再看一次。

**相对旧记录的变化：** 上线前待验证

**相关发言人/执行人：** @[张三](mention://…/user/…)

**录制依据：** 11:05–11:48
```

| 字段 | 取值 |
| --- | --- |
| `title` | H3 标题文字，去掉 `[编号]` 前缀 |
| `description` | 正文，再依次加上 `相对旧记录的变化：…`、`录制依据：…` 等其余加粗字段 |
| `statusNote` | 从正文中摘出表示进展的原句，如「内部5人试用已完成，多数场景可用；弱网环境下同步仍慢」 |
| `status` | 按 §6 判断 |
| `owners` | `**相关发言人/执行人：**` 或 `**负责人：**` 后面的人，按 §8 解析和填 `role` |
| `due` | 正文里的时间表述，如「中秋前」 |
| `parentCode` | 卡片文字写出了所属模块（编号，或与模块标题完全相同的名称）时填该模块的编号；否则留空，不要按主题猜 |
| `relatedCodes` | 只填卡片文字里写出的编号，或用户明确指出的编号；否则为空 |

### 4.4 勾选清单和编号列表

- 一项算一条 task：`- [x]` 的状态为 `done`，其余状态按 §6 判断。标题取该项文字，去掉 @提及。
- **注记行不是条目**：以「状态」「依赖」「说明」「备注」等标签开头的列表项，属于它上面最近的那一条。标签可能是真加粗（`**状态：**`）、被转义的加粗（`\*\*依赖：\*\*`），也可能不加粗（`状态：`）。
  - 「状态」类并入那一条的 `statusNote`；「依赖」「说明」「备注」类并入 `description`（一行 `依赖：…`）。
  - 不编号，不写 `[编号]`。
- **关于其他内容的元说明也不是条目**，例如「原接口文档、演示视频…仍保留」这类说明哪些旧内容还保留的话：并入上一条的 `description`，或者略过。
- 注记行写明上一条「与 <项目> 的 <编号> 为同一任务……不另计」时，上一条按 §11 建镜像。

例：「示例项目」的当前部分是一个 4 项清单——第 1 项是任务（「@赵六 安装包重新打包…」），第 2 项是 `\*\*状态：\*\*…与示例平台待办事项的0916-04为同一任务，此处为项目关联视图，不另计一项任务`，第 3 项是 `\*\*依赖：\*\*…`，第 4 项是「原接口文档…仍保留」。结果只有**一条**条目：第 1 项建成指向「示例平台」`0916-04` 的镜像，第 2 项并入它的 `statusNote`，第 3、4 项并入 `description`；文档里只有第 1 项写 `[编号]`。

## 5. 条目格式（完整快照；旧结构）

### 5.1 字段

同步请求里的每一条条目只能包含下面这些键，多出任何键都会被拒绝（422）：

```jsonc
{
  "code": "K03",                          // 必填，格式必须与 type 一致
  "type": "module",                       // 必填：task | module | milestone | risk
  "title": "…",                           // 必填，≤200 字
  "description": "…",                     // ≤5000 字
  "status": "in_progress",                // 必填，见 §6
  "statusNote": "…",                      // 状态原文，≤500 字
  "due": {"text": "9月底", "start": "2026-09-21", "end": "2026-09-30", "precision": "xun"},
  "startDate": null,                      // 文档有「本周启动」「下下周起」这类开始说法时按 §7 填写，没有就是 null
  "owners": [{"name": "张三", "userId": "…", "role": "负责人"}],
  "priority": null,                       // 文档里写了 P0/P1 等时填写
  "parentCode": null,                     // 父条目编号，不能是自己
  "relatedCodes": [],                     // 关联条目编号
  "source": {"docUrl": "https://outline.example/doc/…", "docId": "…", "heading": "模块与任务状态"},
  "sourceMeeting": {"label": "2026-09-16 需求对齐会", "date": "2026-09-16", "url": "https://outline.example/doc/…"},
  "mirrorOf": null                        // 跨项目镜像，见 §11
}
```

- 可选字段不写或写 `null` 都表示「没有」。
- 所有链接（`source.docUrl`、`sourceMeeting.url`、`meeting.url`）都必须以团队的 Outline 地址（`https://outline.hub.xzs`）开头，否则会被拒绝。本文示例中的 `https://outline.example` 只是占位，实际一律用 `fetch` 返回的链接。
- 同一次同步里，编号不能重复，也不能同时出现在 `items` 和 `removals` 里。

### 5.2 与看板现有条目合并

同步是**整条覆盖**：条目里没写的字段会被清空。看板上已有的条目按来源分两种处理。

**完整定义的条目**：里程碑、模块、风险、待办表的行、成为待办的卡片、清单条目。当前部分的这一行（这张卡片）就是它的全部信息。

1. 所有字段都按文档重新生成。文档里已经不写的日期、负责人、描述，就是 `null` 或空，**不要**从看板现值带过来。例如模块行改成「尚无起算日期，不直接按20天推算上线日」、不再写「约9/30」，那么它的 `due` 就清空。
2. 只有文档里没有的字段沿用看板现值：`sourceMeeting`；文档没有优先级列时的 `priority`；用户以前确认过的 `parentCode`、`relatedCodes`。

**部分信息的条目**：「原任务状态更新」表里看板上已有的行（§4.2 第 1 种情况）、跨项目镜像（§11）。文档只给出状态等少数字段。

1. 从 `board_list_items` 的结果里取出这条条目，作为底稿。
2. 删掉不属于输入的键：`id`、`projectId`、`removed`、`createdAt`、`updatedAt`，以及 `source.url`。
3. 只用文档给出的信息覆盖对应字段（§4.2、§11），其余字段原样保留。

两种都适用：`source.heading` 变了（例如条目移到了新表格，或者标题加了 `[编号]`）时，把 `source.anchor` 设为 `null`，让服务端重新计算。

dryRun 时这样核对 `updated[].fields`：完整定义的条目，每个变化的字段都应能在文档里找到原因（文档删掉了日期，`due` 变空是正常的），找不到原因就是抽取有误；部分信息的条目只应出现文档给出的字段（`status`、`statusNote`、`source`，给了新时间时还有 `due`、`description`），出现别的字段说明底稿漏带了字段，要补齐。

## 6. 状态对照表（旧结构）

| status | 显示 | 典型原文 |
| --- | --- | --- |
| `not_started` | 未开始 | ⬜、未开始、需求设计、方案下周出、计划、待排期、下下周启动 |
| `in_progress` | 进行中 | 🔶、开发中、推进中、基本跑通、首版已出、已启动、调试中、沟通中、方案讨论、放缓但持续跟进 |
| `blocked` | 阻塞 | 审批卡点、等待外部、未获认可且暂无替代方案、卡在某个前置条件上 |
| `to_verify` | 待核实 | 待反馈核实、结果待核实、会上报告完成但未验收、据汇报已完成、未获取会后结果、无完成证据 |
| `done` | 已完成 | ✅、已完成并交付、会上明确完成并关闭、会上确认已完成 |
| `paused` | 暂停·取消 | 暂停、取消、转向、放弃、不再跟进 |

**状态只由文档文字决定**，与哪天同步无关：同一篇文档，今天同步和三天后同步必须得到相同的状态。不要因为时间节点已经过了（相对今天）就改判 `to_verify`；逾期由页面按截止日期自动标出。

按以下顺序判断，取第一条符合的：

1. 明确写了暂停、取消、转向、放弃 → `paused`。写的是「放缓」「不是取消」时仍然算 `in_progress`。
2. 明确写了完成、交付、关闭，并且**这一条自己**没有「待验收」「待核实」「未验收」「仅为会上汇报」之类的限定 → `done`。「会上确认已完成」「会上明确完成」算 `done`；「会上报告完成」「据汇报已完成」算 `to_verify`。
3. 文字本身写了待核实、未验收、结果待核实、未获取（会后）结果、无完成证据 → `to_verify`。
4. 写了卡点、阻塞、等待外部、未获认可，而且目前推进不下去 → `blocked`。
5. 写了推进中、开发中、已启动、沟通中，或带 🔶 → `in_progress`。
6. 其余还在计划中、没有启动的 → `not_started`。

- 整个当前部分或整张表开头的总括说明（如「下列为会上状态，非会后独立验收」）不是某一条的限定，不影响逐条判断。
- 一行里既有暂停的部分、又有仍在推进的部分（如「日志归档暂停，李四改做新版本；9月底上线」）：仍按第 1 条判为 `paused`，但把两部分都写进 `statusNote`，并列入汇报的「待确认」，由用户决定状态。
- 表情和文字矛盾时以文字为准，例如「✅ 基本完成，待验收」→ `to_verify`。
- `statusNote` 始终保留原文，页面会把它作为备注显示。
- 拿不准时选更保守的状态（不判 `done`），并在汇报的「待确认」里列出。

## 7. 日期推算（旧结构）

- `due.text` 一律保留原文（≤100 字）。
- **基准日期是来源会议的日期**，不是今天。例如当前部分标题是「当前待办（2026-09-22会议）」，基准就是 2026-09-22；「明天」即 9/23。
- 没写年份时，取基准日期所在的年份；如果这样得到的日期比基准早三个月以上（例如 12 月的会议里写「1/15」），改为下一年。
- 节假日以当年的官方安排为准（例如 2026 年中秋节是 9/25，国庆节从 10/1 开始）。
- 时间窗含首尾两天。

| 原文（基准 2026-09-22，周二） | start | end | precision |
| --- | --- | --- | --- |
| 9/23、9月23日、2026-09-23 | 2026-09-23 | 2026-09-23 | day |
| 明天 | 2026-09-23 | 2026-09-23 | day |
| 9/24（周四）、本周四 | 2026-09-24 | 2026-09-24 | day |
| 9/28或9/29 | 2026-09-28 | 2026-09-29 | day |
| 9/20前、9月20日前 | 2026-09-20 | 2026-09-20 | day |
| 本周、本周内 | 2026-09-22 | 2026-09-27 | week |
| 下周 | 2026-09-28 | 2026-10-04 | week |
| 下下周 | 2026-10-05 | 2026-10-11 | week |
| 中秋前 | 2026-09-18 | 2026-09-24 | week |
| 国庆前 | 2026-09-24 | 2026-09-30 | week |
| 月底、9月底 | 2026-09-21 | 2026-09-30 | xun |
| 10月底 | 2026-10-21 | 2026-10-31 | xun |
| 11月初 | 2026-11-01 | 2026-11-10 | xun |
| 11月中、11月中旬 | 2026-11-11 | 2026-11-20 | xun |
| 10月、10月内 | 2026-10-01 | 2026-10-31 | month |
| 下月 | 2026-10-01 | 2026-10-31 | month |
| 约9/30、9/30左右 | 2026-09-27 | 2026-10-03 | fuzzy |
| 国庆节后部署，约一周（假设节后首个工作日为 10/8） | 2026-10-08 | 2026-10-15 | fuzzy |
| 国庆前方案定稿；11月中；12月（一行多个节点） | 2026-09-24 | 2026-09-30 | week（取最近的节点，见下） |
| 接口文档确认后约20天（起算日未知） | — | — | — |
| 尽快、待定、待排期、下次迭代会确认 | — | — | — |

规则小结（每条都是确定的，不要自行放宽或收窄）：

- 具体某天 → `day`；「X前」接具体日期 → 当天 `day`；「X前」接节日 → 节日前 7 天 `week`。
- **本周、本周内** → 会议日期到当周周日（`week`）；**下周** → 下周一到下周日；**下下周** → 再下一周的周一到周日。
- 上旬、月初（1–10 日）、中旬、月中（11–20 日）、下旬、月底（21 日到月末）→ `xun`；整月 → `month`。
- **约 X、X 左右** → X 前 3 天到 X 后 3 天，`fuzzy`。依赖条件、给出持续时间的说法（如「节后部署约一周」）→ 从能确定的起点算起，`fuzzy`；起点不确定就推算不出。
- **一行写了多个节点**（如「国庆前方案定稿；11月中；12月」）：`due` 取以会议日期为准、最早的一个文字里没写已完成的节点，`due.text` 写这个节点的原文（如「国庆前方案定稿」）；其余节点原文写进 `description` 一行 `后续节点：11月中；12月`。只有节点之间是二选一（如「9/28或9/29」）时，才用覆盖全部节点的时间窗。
- **表示开始的说法**（「本周启动」「下周起」「下下周起」「10月起」）**一律**写进 `startDate`，取所指时间窗的第一天：本周启动 → 会议日期；下周起 → 下周一；下下周起 → 下下周一；10月起 → 10/1。同一句里没有截止时，`due` 只写原文，`start`/`end`/`precision` 为 `null`。没有这类说法时 `startDate` 为 `null`。
- 推算不出时，`due` 只写 `text`，`start`、`end`、`precision` 为 `null`。这样的条目不会画在时间线上，只列在「无日期」泳道。
- `end` 早于 `start` 时，服务端会丢弃时间窗并给出提醒。这种情况要回头检查推算。

## 8. 负责人（旧结构）

- Outline 提及的格式是 `@[姓名](mention://<提及id>/user/<userId>)`（写入时也可能是 `mention://user/<userId>`）。`userId` 取 `/user/` 后面那段 UUID，第一段是每次提及各不相同的 id，不要用。
- **纯文本 `@姓名`**（没有提及链接）：**不要**按空格或标点切分姓名。中文里姓名后面常常直接接别的字，如「@王小明协助供应商协调」「@王小明与@赵小红」，按标点切会得到「王小明协助供应商协调」这样的名字。做法是：用文档里出现的人名（「人员按本场确认：…」这一行、同一文档里其他提及的姓名）和 Outline MCP `list_users` 返回的姓名，匹配 `@` 后面**最长**的那个人名。
  - 匹配到有 Outline 账号的人：填上 `userId`（纯文本写法也要填，同一个人不能有时带 userId、有时不带）。
  - 只在文档名单里出现、没有 Outline 账号：只记 `{"name": "姓名"}`。
  - 都匹配不上：列为待确认。
- 同一个 userId（或者没有账号时同一个姓名）只记一次，保持在原文中出现的顺序，最多 20 人。
- `role` 按来源填写：
  - 「责任人」「负责人」列，原文写明「负责人：」，待办表「待办内容」里的 @提及，以及历史原文里旧待办的 @提及（§4.2）→ `负责人`
  - 「执行人」列 → `执行人`
  - 「相关发言人/执行人」这类不区分角色的列或字段、正文里顺带提到的人 → `相关人`；文档写明列出的是本场汇报人（如「本场汇报人」「汇报人：」）→ `汇报人`
  - 当前部分写明保留的旧负责人（如「采集模块原负责人赵六保留」「明确保留两者」时点名的旧负责人）→ 另外加上此人，`role` 为 `负责人`
- 「发言人3」这类匿名标签不要当作负责人，在汇报里列为待确认。

## 9. 编号规则与写回（旧结构）

### 9.1 编号规则

| 类型 | 格式 | 说明 |
| --- | --- | --- |
| task | `MMDD-NN`，如 `0922-01` | 待办出自的会议日期加两位序号；最多到 99，用完后服务端返回 `code_exhausted`，这时问用户怎么处理 |
| module | `K01`、`K02`…`K100` | 至少两位数字 |
| milestone | `M01`… | |
| risk | `R01`… | |

- 编号在**项目内**唯一，不分类型：`K03` 只能是模块，`0922-01` 只能是一条待办。
- 已有编号永不改动。已移除条目的编号也不再分配给别的事项，`next-code` 已经考虑了这一点。
- **本次会议的新待办，以及新的模块、里程碑、风险**：新号 = max(`next-code` 返回的号，文档里（含历史部分）已出现的同类最大号 + 1)，按文档中从上到下的顺序依次分配。
- **补编历史待办按位置**，不用 `next-code`，也不取「最大号 + 1」：
  - 那次会议原待办列表里的第 N 条 → `MMDD-NN`。例如只提到了 9/10 待办列表的第 4 条，它就是 `0910-04`，不是 `0910-01`。
  - 那次会议已有编号表（如 `0916-01`～`0916-04`）、另有没编号的清单（如「转写补充执行项」）时，清单条目接在表中最大号之后，按文档顺序继续：清单第 1 条 → `0916-05`。
  - 按位置算出的号即使暂时没用到也算已占用，不再分给别的事项。
  - 可能对应不止一条旧待办时，列出候选请用户选；按位置算出的号在看板上已属于别的条目时，也问用户。

### 9.2 文档里已有的编号

以下位置的编号算作条目编号：

- 表格「编号」列，或「原编号/任务」列开头的 `MMDD-NN`、`K01`、`M01`、`R01`
- 标题开头的 `[编号]`，如 `### [0922-10] 用户试用反馈`
- 风险条目、清单条目里的 `[编号]`（§9.3 的写回位置）

正文里的「见 0916-03」「与 K05 相关」「与示例平台待办事项的0916-04为同一任务」只是引用，不是定义。

### 9.3 写回格式

| 位置 | 写回前 | 写回后 |
| --- | --- | --- |
| 没有编号列的表格 | `\| 时间/条件 \| 交付或动作 \| 状态与边界 \|` | `\| 编号 \| 时间/条件 \| 交付或动作 \| 状态与边界 \|`；分隔行开头加 `\|----`；每行开头加 `\| M01 ` |
| 已有编号列的表格 | 编号单元格为空 | 填上编号 |
| 「原编号/任务」列 | `\| 9/10 日志归档方案 \|` | `\| 0910-01 9/10 日志归档方案 \|`（原文一字不改，只在前面加编号） |
| 成为待办的卡片式 H3 | `### 供应商合同核对` | `### [0922-10] 供应商合同核对` |
| 风险引用块 | `> ⚠️ **接口联调排期：** …` | `> ⚠️ **[R01] 接口联调排期：** …` |
| 风险列表（加粗） | `* ⚠️ **数据合规评审：** …` | `* ⚠️ **[R02] 数据合规评审：** …` |
| 风险列表（不加粗） | `* ⚠️ 上线时间紧迫：…` | `* ⚠️ [R03] 上线时间紧迫：…` |
| 没有 ⚠️ 的风险条目 | `- 上线时间紧迫：…` | `- [R03] 上线时间紧迫：…` |
| 勾选清单 | `- [ ] @张三 推进…` | `- [ ] [0922-11] @张三 推进…` |
| 编号列表 | `1. 出具日志归档方案。 @李四` | `1. [0910-01] 出具日志归档方案。 @李四` |

风险的规则是：`[编号]` 紧跟在 `⚠️ ` 后面；有加粗标题时写在加粗里面；没有 `⚠️` 时写在引用符号或列表符号后面。由模块覆盖、并入已有待办的卡片（§2.2）和清单注记行（§4.4）不写编号。

### 9.4 patch 操作要点

- 只用 `update_document`，`editMode: "patch"`，`findText` 为旧文本，`text` 为新文本。
- `findText` 必须从**最新的** markdown 中原样复制，包括提及链接、表格对齐用的空格和 `|-------|` 分隔行。最新的 markdown 指：本篇文档第一次 patch 前 `fetch` 的结果；之后是上一次成功 patch 在结果里返回的整篇 markdown。只有 patch 找不到匹配或报错时才重新 `fetch`。
- 一次 patch 处理一张完整的表格（表头、分隔行和全部数据行）、一个标题或一整个风险引用块 / 风险列表。
- patch 只替换**第一处**匹配。当前部分在文档开头，一般第一处匹配就在当前部分；但同样的表格或引用块也可能在别处重复出现（例如待办事项「时间节点与风险」里的里程碑表），所以要确认第一处匹配位于当前部分。为保险起见，可以把表格上方的标题行一起放进 `findText`。
- 文本没有任何变化的 patch 会被 Outline 当作错误返回，不要重复提交已经写好的编号。
- 写完用最后一次 patch 返回的 markdown（拿不到时重新 fetch）核对：编号齐全、行数不变、提及仍是提及，其他文字没有变化。
- 第一次给某篇文档写回后，提醒用户打开 Outline 看一眼表格是否正常。万一渲染异常，可以用 Outline 的文档历史恢复。

## 10. 出处（旧结构）

- `source.docUrl`：条目所在文档的链接，取 `fetch` 返回的 `url`；`source.docId`：该文档的 id。
- `source.heading`：条目上方最近的标题文字，不带 `#`，并且是**写回编号之后**的样子。表格行取表格上方的标题，如「模块与任务状态」；卡片式小节取卡片自己的标题，如「[0922-10] 供应商合同核对」。
- `source.anchor` 一般不填，服务端会按 Outline 的规则用标题算出锚点。文档里有同名标题（如两个「当前里程碑」）时，服务端按第一次出现计算。所以尽量选文档里唯一的标题；实在没有，链接跳到第一个同名标题也可以接受。
- **会议的 label** 统一写成 `YYYY-MM-DD 会议名`。会议名按顺序取：
  1. 进度追踪或待办事项（当前或历史部分都可以）里引用这份纪要的「来源」链接文字，如「来源：[示例项目研发周会](…)」→「示例项目研发周会」；
  2. 没有这样的链接时，用纪要标题：一层的新标题 `YYYY-MM-DD 会议主题` 去掉开头的日期和空格（「 HH:MM」后缀保留），这样 label 就是纪要标题本身；旧标题去掉开头的「HH:MM-HH:MM 」时间段；
  3. 去掉后只剩会议室默认名（如「3楼会议室的个人会议室」）时，问用户。

  同一次会议在请求顶层的 `meeting` 和各条目的 `sourceMeeting` 里，label 必须完全相同。
- `sourceMeeting`（条目首次出现的会议）：
  - 待办：按编号里的日期，在项目「会议纪要」下找标题以该日期开头的纪要，没有再找旧的「会议纪要 / YYYY-MM-DD」目录里的纪要，填 `{"label": "YYYY-MM-DD 会议名", "date": "YYYY-MM-DD", "url": 纪要链接}`；找不到纪要时只填 `label` 和 `date`。
  - 看板上已有的条目：沿用看板现值。
  - 新的模块、里程碑、风险：填本次会议。
- 请求顶层的 `meeting`（本次同步所依据的会议）：取当前部分注明的来源会议，如「来源：[示例项目周会](…)」加上标题里的日期。全量重建又没有对应会议时，可以设为 `null`。

## 11. 跨项目镜像（旧结构）

同一件事可能出现在另一个项目里，例如「示例项目」的当前部分写着要跟进「示例平台」的待办 `0916-04`。这时不复制内容，而是在**引用方项目**里建一条镜像条目：

```json
{
  "code": "0916-01", "type": "task", "title": "安装包重新打包与版本一致性更新",
  "status": "in_progress", "statusNote": "与示例平台待办事项的0916-04为同一任务，此处为项目关联视图，不另计一项任务",
  "mirrorOf": {"projectId": "<示例平台在看板上的项目 id>", "code": "0916-04"},
  "source": {"docUrl": "…", "docId": "…", "heading": "…"}
}
```

- 文档写明某条与另一个项目的某个编号「为同一任务」时，只从**任务那一行**建**一条**镜像，把写着「同一任务……不另计」的那一行并入它的 `statusNote`（§4.4）。
- 镜像的 `code` 是引用方项目**自己的**编号：该条出自的会议日期下的下一个可用号（`next-code` 与本项目文档里当天最大号 + 1 取大，例如「示例项目」当前部分是 9/16 的补充待办，就是 `0916-01`），写回本项目的文档。**绝不照抄原项目的编号**，即使原文里写着「0916-04」。
- `type` 和 `title` 与原条目一致。`status` 必须填写，可以照原条目当前的状态填；页面上会显示原条目的**实时**状态，并标注「来自 示例平台」。
- 镜像是部分信息的条目（§5.2）：看板上已有时以看板现值为底稿。
- 原项目的 id 用 `board_list_projects` 查询。原项目还没在看板登记时，不建镜像，当作本项目的普通条目处理，或者问用户。
- 需要引用方项目的写权限；新建或修改镜像时，还需要你在 Outline 中能读取原项目。读不到时服务端返回 422「镜像来源项目不存在，或你在 Outline 中没有该项目的读取权限」：不要换个写法重试，改为普通条目或问用户。已存在且没有改动的镜像照常同步。

## 13. 旧结构的同步步骤（原 SKILL.md 第四～八步的旧结构部分）

只在用户明确坚持按旧结构同步时使用。前置检查、首次登记、dryRun 与正式同步的顺序和 SKILL.md 相同；下面只写旧结构不一样的地方。汇报末尾要再提示一次：这个项目还是旧结构，可以用 outline-promeeting-update 迁移。

### 13.1 定位

项目是直接子文档里同时有「进度追踪」和「待办事项」的那一层（SKILL.md 第二步）。只找到其中一篇、有多个候选层级时，列出候选请用户确认。

### 13.2 读取与抽取

1. 用 `fetch` 读取「进度追踪」「待办事项」的全文。
2. 用 `board_list_items`，参数 `includeRemoved: true`（CLI：`items <项目ID> --include-removed`），取得看板上现有的全部条目，按编号建立对照。
3. 区分**当前部分**和**历史部分**（§1：分界线是后面紧跟历史标题的那条 `---`，卡片之间的 `---` 不算）。**只从当前部分抽取条目**；历史部分只能查阅（例如查沿用编号条目的原始表述），不抽取，也绝不修改。
4. 按 §2–§4 的映射抽取。表格按**作用**识别，列名和这里写的不一样也能对应（§2.1）：
   - 进度追踪当前部分：里程碑表 → 里程碑 `M`；模块/任务状态表 → 模块 `K`；风险引用块或风险列表 → 风险 `R`
   - 待办事项当前部分：带 `MMDD-NN` 编号的待办表、「原任务状态更新」表、卡片式 H3 小节、勾选清单 → 待办 `task`
   - **同一件事只留一条**（§2.2）：与进度追踪某个模块同名的卡片由该模块覆盖，不另建待办；文档写明卡片「不表示重复新建同一任务」时，复述已有待办的卡片也不另建。清单里的「状态：」「依赖：」等注记行并入上一条，不算条目（§4.4）。
   - 当前部分的表格对不上任何作用、某列不知道对应什么字段时，先问用户。
5. 抽取时记下每条条目在文档中的位置（哪篇文档、哪张表第几行、哪个标题），写回编号要用。
6. 当前部分缺少某一类内容，而这类内容只出现在历史基线里时（例如当前部分只有一段文字，模块表只在「9月1日历史基线」里），**不要从历史部分抽取，也不要往历史部分写编号**。告诉用户，并建议迁移到「进度与待办」。

### 13.3 编号与写回

1. **沿用**：文档里已经有编号的条目直接用原编号，永远不要改动已有编号。包括上次写回后没来得及同步、看板上还没有的编号。
2. **对上旧条目**：没有编号、但和看板上已有条目明显是同一项（同类型、标题相同或基本相同）的，沿用看板上的编号。拿不准就问用户。
3. **编新号**：
   - **本次会议**的新待办：`board_next_code`，参数 `type: "task"` 加 `meetingDate`（CLI：`next-code <项目ID> --type task --meeting-date YYYY-MM-DD`）。新号 = max(`next-code` 的结果, 文档里（含历史部分）当天已用的最大号 + 1)，按文档中从上到下的顺序依次分配。
   - 模块、里程碑、风险：`type` 设为 `module`、`milestone` 或 `risk`，同样与文档里已有的最大号取大，按文档顺序依次取号。
   - **补编历史待办**（当前部分在跟进、但原来没有编号的旧待办）：**按位置编号**，不用 `next-code`（§9.1）。
   - 一行可能对应不止一条旧待办时，**列出候选请用户选**；按位置算出的号在看板上已属于别的条目时，也问用户（§4.2、§9.1）。
4. **写回格式**（§9.3）：
   - 表格没有编号列：新增「编号」作为第一列
   - 表格已有编号列：填空着的单元格
   - 第一列是「原编号/任务」这类混合列：在单元格开头加上编号
   - 成为待办的卡片式小节：在标题前加 `[编号]`，如 `### [0922-10] 用户试用反馈`；由模块覆盖或复述已有待办的卡片不写编号
   - 风险：`[编号]` 紧跟在 `⚠️ ` 后面，有加粗标题时写在加粗里面，如 `> ⚠️ **[R01] 接口联调排期：** …`、`* ⚠️ [R02] 上线时间紧迫：…`
   - 清单条目：写在勾选框或序号后面，如 `- [ ] [0922-11] …`
5. **写回方式**：与 SKILL.md 第五步相同（只用 `update_document` 的 `patch`，findText 原样复制，核对，失败不改用 replace/append/prepend），另外：
   - 一次 patch 只改一张表、一个标题或一个引用块。patch 只替换第一处匹配，所以要确认第一处匹配落在**当前部分**；必要时把表格上方的标题行也放进 `findText`（§9.4）。
   - 写回之前的一句话，例如「进度追踪：里程碑表和模块表各加一列编号，风险加 [R01]–[R05]；待办事项：3 个卡片标题加编号」。
6. **中断后的恢复**：写回中途失败时，已经写进文档的编号保留不动，下次运行时按第 1 条当作已有编号。其中「原任务状态更新」表里的编号，按 §4.2 的第三种情况（文档有编号、看板没有）重建条目。
7. 绝不写：会议纪要、「看板」文档、总看板文档集首页，以及两篇文档的历史部分。

### 13.4 规范化

- **每条都是完整快照**，按条目来源分两种（§5.2）：
  - **完整定义的条目**（里程碑、模块、风险、待办表的行、成为待办的卡片、清单条目）：字段全部按文档重新生成。只有文档里没有的字段沿用看板现值：`sourceMeeting`；文档没有优先级列时的 `priority`；用户以前确认过的 `parentCode`、`relatedCodes`。
  - **部分信息的条目**（「原任务状态更新」表的行、跨项目镜像）：以 `board_list_items` 取到的现值为底稿，只覆盖文档给出的字段。
- **状态**：按 §6 从文字判断，原文写进 `statusNote`。状态只由文档文字决定，与同步那天是几号无关；拿不准时选更保守的状态。
- **日期**：`due.text` 保留原文；时间窗按 §7 以**来源会议日期**为基准推算，推算不出就留空。开始类说法写进 `startDate`。
- **负责人**：按 §8 取 userId、匹配纯文本姓名、填 `role`（负责人 / 执行人 / 汇报人 / 相关人）。
- **出处与会议**：按 §10。`source.heading` 按写回编号**之后**的文字填写。

### 13.5 同步请求

- **增量**：`items` 放当前部分的全部条目；只出现在历史部分的旧条目不用放。`removals` 只放在两篇文档里（含历史部分）**已完全找不到**的编号。
- **全量重建**：`items` 放当前部分的全部条目，再加上看板上已有、而且编号在文档里（含历史部分）仍能找到的条目（沿用看板现值）。
- dryRun 自查时，**部分信息的条目**（状态更新行、镜像）的 `updated[].fields` 只应出现文档给出的字段（`status`、`statusNote`、`source`，给了新时间时还有 `due`、`description`）；出现别的字段说明底稿漏带了字段，补齐后再 dryRun（§5.2）。

### 13.6 汇报

```
由模块覆盖、未单独建待办：<卡片标题> → K05、…；并入已有待办：<卡片标题> → 0922-04、…
编号写回：进度追踪 <处数>（链接）；待办事项 <处数>（链接）
未进入看板：<只在历史部分、或无法定位的内容>
提示：「<项目名>」还是旧结构，建议用 outline-promeeting-update 迁移成「进度与待办」
```
