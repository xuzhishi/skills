# Outline 会后同步（会议纪要 → 进度与待办 / 项目文档）

## 概述

本 skill 把"根据一份 Outline 会议纪要，同步更新项目文档"的完整流程标准化：

1. **确认整理人，定位并阅读会议纪要**
2. **找出相关项目并请用户确认**：一场会可能涉及几个项目；按纪要所在、纪要点名、讨论到其条目、跨项目关联四种依据在 Outline 里查找，列出依据，用户确认后才写
3. **阅读每个项目的文档**：「进度与待办」首页、最近的会议子文档、「项目文档」
4. **深度分析**：逐条拆解会议内容，确定每项内容属于哪个项目、落到首页哪一行、子文档记哪种变化、是否影响项目文档
5. **新建会议子文档**（每个项目一篇）：只记本次变化、本次决定、新增缺口
6. **重写「进度与待办」首页**（每个项目）：固定模板，当前全貌
7. **按需更新项目文档**
8. **校验、排序与汇报**：确认会议纪要未被改动；核对每个项目目录的顺序（看板、进度与待办、项目文档、会议纪要在最前面），不对就移好；向用户汇报
9. **同步看板和总看板**：若已安装 outline-board-sync，对每个更新过的项目做一次增量同步，再核对总看板

核心原则：**只新增和更新目标文档，绝不删改会议纪要；相关项目全部找出、经用户确认后逐个更新；首页写当前全貌，子文档只记变化；人名一律 @，写明谁整理、谁写的纪要；有疑问先问，不猜。**

## 一、定位并阅读会议纪要

1. 先 `fetch`（resource=user，id=current_user）：返回的人就是 MCP 里这个 Outline token 的主人，也就是本次的**整理人**（常常是产品经理，不一定是主持人或汇报人）。取不到时问用户，不要猜
2. 纪要来自用户给的 **URL 或标题**，或者是 meeting-to-outline 刚归档的那篇（它归档完会接着转到本技能）。用 Outline MCP 的 `fetch`（resource=document）读取全文；同时记下返回的 `createdBy`、`createdAt`、`updatedBy`、`updatedAt`，写进子文档页首（第五节）。时间是 UTC（末尾带 `Z`），换算成北京时间
3. 仔细阅读并逐项记录：
   - 会议主题、时间、参会人/发言人
   - 会议摘要与核心结论
   - 逐条决策事项（含被否定/变更的旧方案，这能解释文档里旧内容的来龙去脉）
   - 逐条待办事项 + 责任人
   - 风险点、时间节点、未决事项
4. 阅读时记下纪要里出现的**每一个人名**（用于后续 @，见第七节）；若只有「发言人1」「Rooms会议室-发言人N」等匿名标签，记下这一点，稍后向用户确认对应关系
5. 纪要标题形如 `YYYY-MM-DD 会议主题`；旧纪要在日期目录下，标题形如 `HH:MM-HH:MM 主题`，两种都认。

## 二、找出相关项目，阅读项目文档

一场会可能涉及几个项目。要找出**所有**相关的项目，不只是纪要所在的那个，每个都单独更新。项目＝直接包含「进度与待办」的那一层（一篇文档，或整个文档集）；还没迁移的旧项目是直接包含「进度追踪」的那一层。

### 1. 找出候选

按下面四种依据在 Outline 里找，每个候选记下依据（纪要原句和〔mm:ss〕、编号、链接）：

| 依据 | 怎么找 |
| --- | --- |
| 纪要所在的项目 | 从 `fetch` 纪要得到的 `collectionId`、`parentDocumentId` 出发，用 `list_collection_documents` 逐级向上，第一个直接子文档里有「进度与待办」（或「进度追踪」）的节点。纪要在个人文档集、普通文档集里时没有这一项 |
| 纪要点名的项目 | 纪要标题、摘要、会议内容、待办里出现的项目名、产品名：`list_collections`（`query`＝名字）找同名文档集，`list_documents`（`query`＝名字）找同名文档，按结果的 `breadcrumb` 定位到项目这一层 |
| 讨论到其条目的项目 | 纪要里说到的编号（`MMDD-NN`、`K01` 等）、模块名、里程碑名、待办标题：`list_documents`（`query`＝编号或名称）搜，命中在某个项目的「进度与待办」首页、会议子文档或「项目文档」里，这个项目就是候选。编号只在本项目内唯一，编号和名称都对得上才算依据 |
| 跨项目关联 | 已找到的项目首页里，本次讨论到的行「关联」写着「镜像 项目名 编号」，或进展里写明和另一个项目的某个编号是同一任务（如「示例平台 0916-04」）→ 那个项目；再用 `list_documents`（`query`＝「镜像 <项目名>」）找镜像了这些条目的其他项目 |

- `list_documents` 带 `query` 就是 Outline 的全文搜索，结果带 `breadcrumb` 和命中片段 `context`，默认不含已归档文档；只搜得到当前用户有权读的文档。
- 每个候选查一下结构：新结构（有「进度与待办」）、旧结构、迁移没做完、都没有（见下面「目录约定」）；「进度与待办」下已经有这场会的子文档的，标「已更新过」（按模板文件第 22 条处理，不新建）。

### 2. 请用户确认

写任何文档之前，把候选一次列给用户，**确认后才写**，只有一个候选也要确认：

| 项目 | 位置 | 依据 | 结构 | 建议 |
| --- | --- | --- | --- | --- |
| 示例项目 | 研发 › 示例项目 | 纪要在它的「会议纪要」下 | 新结构 | 更新 |
| 示例平台 | 平台 › 示例平台 | 〔12:30〕讨论配网接口，对应它首页的 0916-04 | 新结构 | 更新 |
| 示例商城 | 示例商城（文档集） | 只在〔40:10〕顺口提到一次 | 都没有 | 不更新 |

- 只是顺口提到、对不上具体条目的，建议「不更新」，由用户决定。
- 同时说明：只搜得到你有权读的文档，漏掉的项目请直接告诉我。
- 旧结构要迁移、都没有要创建「进度与待办」的，在这一步一起问（规则见下面「目录约定」）。
- 用户可以增减；只更新用户确认的项目，不自行增减。一个候选都没有时，问用户要更新哪个项目；用户说都不用就停下，在汇报里说明。

### 3. 阅读每个项目的文档

对每个确认的项目分别：

1. 用列文档树工具（如 `list_collection_documents`）列出项目目录结构
2. 找到并读取：
   - 「进度与待办」首页全文（它就是上一版，写新版前必须读）
   - 「进度与待办」的子文档列表，以及最近几篇子文档（查编号、查决定）；编号要取「当天已用的最大号」时，读全部子文档
   - 「项目文档」目录下的所有文档（PRD、需求、设计等，含子文档）
3. 相关但未读的文档也要读（如更早的会议纪要、关联 PRD），避免遗漏上下文

### 4. 每个项目单独更新

- 第三～七节对每个确认的项目各做一遍：各读各的首页和子文档，各建一篇会议子文档（标题都与纪要逐字相同，都链接同一篇纪要），各自整篇重写首页。每个项目只写属于它的内容，编号按各自的序列编；本次对某个项目没有变化，也建一篇、「本次变化」写「无。」。
- 同一件事涉及两个项目：原条目写在负责它的项目；另一个项目要跟踪时写一行镜像（本项目的编号，关联「镜像 <负责项目名> <原编号>」）。归属拿不准时问用户。
- 人名一次问完，对所有项目都适用；整次运行只取一次当前时间，所有项目的「整理」「最近更新」都用它。
- 一个项目写完（子文档、首页、核对、目录顺序）再写下一个；某个项目失败，已写好的不回退，在汇报里说明。
- 细则见模板文件第 32 条。

### 目录约定

| 文档/目录 | 类型 | 用途 |
| --- | --- | --- |
| 看板 | 文档 | 看板服务生成的嵌入页面，**不要编辑** |
| 进度与待办 | 文档 | 首页＝当前全貌（里程碑、模块、风险、缺口、待办）；子文档＝每次会议的变化「YYYY-MM-DD 会议主题」 |
| 项目文档 | 容器 | 内含 PRD 等需求/设计文档 |
| 会议纪要 | 容器 | 会议纪要，一层：「YYYY-MM-DD 会议主题」 |

- **顺序固定**：项目这一层，上表四篇依次排在最前面（缺的跳过，其余照这个相对顺序），其他文档排在后面、相互之间的顺序不动。每次运行都用 `list_collection_documents` 核对，不对就自上而下移好：对第 i 位（i＝0、1、…），应当在这一位的那篇不在，就 `move_document` 把它移到 `index: i`（项目是一篇文档时 `parentDocumentId`＝项目本身那篇文档，不是名为「项目文档」的那篇；项目是整个文档集时改传 `collectionId`），只往上移；移完再列一次核对。新建的标准文档在第 0 位，建好后立刻这样排一次。四篇按标题逐字认，同一层有同名的就不排、在汇报里列出。旧结构和迁移没做完的项目不排，迁移的最后一步（W6）再排。规则和例子见模板文件第 31 条。文档集不是手动排序（`sort.field` 不是 `index`）时这个顺序显示不出来，汇报里提醒用户请管理员改成手动排序。

- **旧结构**（有「进度追踪」「待办事项」、没有「进度与待办」）：先不更新。告诉用户这个项目需要迁移，按 `references/migration.md` 出迁移计划；用户同意、迁移完成后再做本次会后更新。用户不同意迁移就跳过这个项目（其他项目照常），**不再按旧格式写**。
- **迁移没做完**（「进度与待办」和「进度追踪」或「待办事项」同时存在）：这个项目先不写，问用户。
- **都没有**：告诉用户将在项目目录下创建「进度与待办」（和「项目文档」，如果也没有），征得同意后创建，建好后按上面的顺序排好；不再创建「进度追踪」「待办事项」。

## 三、深度分析

逐条处理会议纪要内容，先定它属于哪个确认的项目（只落到一个项目；两个项目都要跟踪的按第二节第 4 小节写镜像；不属于任何确认项目的不写），再建立「更新映射」：

| 会议纪要内容 | 落点 |
| --- | --- |
| 决策与结论 | 会议子文档「本次决定」，和/或项目文档（需求变更） |
| 待办事项 | 首页「待办」（每条原始待办一行），子文档记「新增」 |
| 缺负责人、缺日期、移交不明 | 首页「缺口」 |
| 风险与时间节点 | 首页「里程碑」「风险」 |
| 模块/任务进展表述 | 首页「模块」等各行的状态和进展，子文档记对应的变化 |

同时**评估现有文档的内容与质量**，更新后的文档质量必须高于更新前：

- 旧内容与会议结论冲突的 → 按新结论改写首页，并在子文档记一行变化（原→新、原因、提出人）
- 会议纪要里已澄清、但文档里仍是问号/待定的 → 补全
- 缺章节、缺细节的 → 按会议内容补全
- 结构混乱的 → 重组为清晰层级（会议纪要的正文结构可作为重组依据）
- 写出来的更新必须**完整全面**：会议纪要里涉及的细节（数值、参数、时间、命名、设计点、引导语等）一条不落地落到对应文档。首页和子文档只写结论和事实；数值、参数、讨论细节写进项目文档（第六节），或者留在纪要里。

## 四、重写「进度与待办」首页（固定模板）

首页是项目的**当前全貌**，每次会后按 `references/progress-doc-template.md` 整篇重写。写之前先读完这个文件。

- **骨架**：页首三行引用块（来源、汇总、最近更新）+ 里程碑、模块、风险、缺口、待办五张表 + 「最近会议」清单；表头一律是 `| 编号 | 事项 | 负责人 | 截止 | 状态 | 进展 | 关联 |`；不写 H2、`---`、段落、卡片、本次决定、历史部分。
- **一件事只写一行**，别处只写编号。
- **全量重写**：上一版所有没关闭的编号都要再出现，每一栏都写全；本次关闭的条目在表尾保留一次，下次重写时删去。
- **单一负责人**：负责人格里恰好一个人，其余的人写成「（执行：…）」；汇报人不是负责人，只有会上明确移交才换人；定不下来先问用户，还是定不下来就写「待指定（见 编号）」并建一条缺口行。
- **具体截止**：相对说法按会议日期换算成最晚的那一天，原话写在括号里；改期时累加「原 M/D」，进展里写「延期：原因（@提出人 提出）」；没有日期的写「待定（见 编号）」并建缺口行；只有会上明确决定不设日期，才写「无承诺」。
- **缺口**：缺负责人、缺日期、移交不明，都在「缺口」表建一行正式待办，有负责人（项目负责人或原行负责人）、截止默认下次例会，会同步到看板、过期也算逾期；AI 自己拿不准的事（转写里点的是谁、发言人是谁）当场问用户，不建缺口行。
- **状态**：只用六个词——未开始、进行中、阻塞、待核实、已完成、暂停·取消，不因为日期已过而改状态。
- **编号**：遵守「八」里的「保留看板编号」；所有新编号（待办和缺口的 `MMDD-NN`，模块、里程碑、风险的 `K`/`M`/`R`）在写入前由本技能编好，不留空。
- **最近更新**：页首第三行 `最近更新 @整理人 YYYY-MM-DD HH:MM（依据 [本次子文档](链接)）`，每次重写时整行替换；谁在什么时候更新过，看子文档列表（每篇子文档页首都有整理人）。首页不设变更记录。
- **写入**：先建第五节的会议子文档，再用 `update_document` 整篇重写首页，标题不变；上一版的提及链接尽量留用、每条最多用一次（第七节）。写入前按模板文件的「自检」（第 27 条）逐项检查，写入后重新 `fetch` 核对。

## 五、新建会议子文档（只记本次变化）

- 每次会后在每个更新的项目的「进度与待办」下各新建**一篇**，标题与会议纪要标题逐字相同（`YYYY-MM-DD 会议主题`），几个项目的子文档标题相同、都链接同一篇纪要；先建子文档，再重写首页，首页页首链接到它。
- 页首两行署名：`纪要：[标题](链接) · 创建 @X YYYY-MM-DD HH:MM · 最后编辑 @Y YYYY-MM-DD HH:MM`（取自第一节 `fetch` 纪要的结果，最后编辑的人和时间都与创建相同时省去这一段）；`整理：@整理人 YYYY-MM-DD HH:MM · 会议日期：… · 当前全貌见[进度与待办](…)`，与首页「最近更新」同一个时间。本次有用户确认的名字时，再加一行「身份确认：…」。纪要以后被人改过，也由后来的子文档记下，纪要本身不动。
- 内容只有三节：「本次变化」表（`| 编号 | 事项 | 变化（原→新） | 原因 · 提出人 | 依据〔mm:ss〕 |`，类型为新增、恢复、换负责人、改期、改完成标准、改状态、关闭、进展）、「本次决定」（拍板人、否决的方案、影响的编号）、「新增缺口」。不写全量快照；人名一律 @（第七节）。
- 「本次变化」必须和首页新旧两版的差异一一对应，规则见模板文件。
- `create_document` 会把新子文档放在最上面；补建较早会议的子文档时，用 `move_document` 的 `index` 排到正确位置（新的在上）。同一父文档里往下移时 `index` 要按移动前的位置算，取法见模板文件第 24 条，不要直接传「比它新的篇数」。
- 纪要还在旧日期目录里（标题 `HH:MM-HH:MM 主题`）时，子文档标题用 `YYYY-MM-DD 主题`（日期取日期目录），见模板文件第 20 条。
- 子文档建好后不再修改。发现错误时，经用户同意用 patch 更正，并在文末加一行「更正：YYYY-MM-DD HH:MM @更正人 …」（模板文件第 22 条）。同一场会已经有子文档时不再新建。
- 纪要里的每条原始待办在首页各占一行，不合并；标题取原句，只去掉时间词、句末标给负责人的 @ 和句末标点，句中的人名照样写 @。

## 六、按需更新项目文档

当会议纪要中的决策**改变需求、架构、设计细节**时（如模块更名、交互逻辑调整、新增模块、性能指标变化），同步更新项目文档（PRD 等）：

- 用 `update_document` 更新，保留原有全部内容与图片/链接资产（replace 重写时图片 URL 必须原样保留）
- 新增决策用「★ 会议日期 更新」标注，保留旧表述作为历史参考
- 命名/架构等硬变更直接改写，同时注明来源会议
- 不影响需求的内容（如纯排期讨论）不要硬塞进 PRD
- 决策写进项目文档后，在当次子文档「本次决定」那一条后面附上链接

## 七、人名一律 @（mentions）

- **范围**：本技能写的每一处人名都写 @——首页的项目负责人、负责人格（含「执行」）、事项、进展（提出人、汇报人、拍板人、候选人、移交双方）、最近更新；子文档的纪要创建人和编辑人、整理人、「原因 · 提出人」、拍板人、身份确认、更正行的更正人和确认人。不再只限负责人格。团队、角色、外部单位不是人名，不加 @。
- **查人**：用 `list_users`（`query`＝姓名）把姓名匹配到 Outline 用户（留意同名、昵称、英文名、拼音）。唯一匹配写 `@[姓名](mention://user/<userId>)`，姓名用账号上的名字。
- **没有账号**：写纯文本 `@姓名`，**不能省掉 @**；后面紧跟文字时空一格。
- **先问再写**：写入前把没匹配上的名字、拿不准的名字（同名账号不止一个、只是相近，例如转写里的同音字，或只有称呼）一次列给用户，问正确的名字、是不是外部人员；用确认后的名字写，确认结果记进当次子文档页首的「身份确认」。以前的「身份确认」里确认过没有账号或是外部人员的人，照用，不再问。
- **匿名标签**：「发言人1」「Rooms会议室-发言人N」确认之前原样写，不猜、不 @；用户确认后按上面写，并记进「身份确认」。
- **不重复通知**：Outline 按提及的 id 判断是不是新提及，新提及会给被提及的人发通知；两段写法每次都会生成新 id。所以重写首页时，上一版的提及链接（三段写法 `mention://<id>/user/<userId>`，原样照抄）尽量留用：没改的格照抄，新写的文字提到上一版提及过的人，用他还没被本版用掉的一条旧链接；**每条旧链接最多用一次**（Outline 编辑器会给重复的 id 换新 id，照样通知）。旧链接用完了、或上一版没提及过的人，才写两段写法（模板文件第 4 条）。
- 写入后重新 `fetch`，提及没有渲染出来的在汇报中说明；没有账号、写成 `@姓名` 的人也在汇报中列出。

## 八、规范与安全

- **绝不修改会议纪要**：不编辑、不覆盖、不删除会议纪要及其任何内容
- 任何不清晰之处（项目归属、模块归属、责任人、命名歧义、目标文档位置）→ **先问用户**，不猜
- **只更新用户确认的项目**（第二节）：写之前列出候选和依据，不自行增减；用户不要的候选写进汇报
- 破坏性操作（删除/移动/归档文档）前必须确认。按目录约定调整项目这一层的顺序只改位置、不改内容，不需要另外确认，在汇报里说明
- 更新完成后向用户汇报：改了哪些文档、主要变更点、遗留问题
- **保留看板编号**：「进度与待办」首页和会议子文档里的编号（待办、缺口 `MMDD-NN`，模块 `K01`，里程碑 `M01`，风险 `R01`）是看板同步用的稳定标识。首页「编号」列不得删除、清空、改写，也不得挪到别的条目上；已关闭、从首页删去的编号也不再使用。新编号由本技能按模板文件编好，接着已用的最大号往下编，能调用看板时与 `board_next_code` 的结果取大。
- **不要编辑「看板」文档**：它由看板服务生成，只有一个嵌入，markdown 写入会把嵌入变成普通链接。
- **会议子文档只写一次**：除经用户同意的更正外，不修改已有的子文档。
- **不重建旧文档**：不再创建「进度追踪」「待办事项」；遇到旧结构先迁移（`references/migration.md`）。迁移中的每一次写入（改名、重写首页、建子文档、移动或改名纪要、归档）都要先给用户看，得到同意后执行。

## 九、完成后汇报

向用户列出（几个项目时，第 2～5 项按项目分开写）：

1. 相关项目：更新了哪些；没更新的候选和原因（用户不要、不同意迁移、写入失败）
2. 更新的文档及链接：本次会议子文档、「进度与待办」首页、改动过的项目文档；主要变更摘要
3. 本次延期（编号，原日期→新日期）、逾期未汇报和连续 2 次未提及的行、新建的缺口行、带「（拟）」的完成标准
4. 遗留的疑问/待用户确认的点（点了多人、说法冲突、仍未确认的匿名发言人、项目归属），以及本次用户确认过的身份、没有 Outline 账号写成 `@姓名` 的人
5. 调整过的项目目录顺序：移了哪几篇、移完的顺序（没调整就不提）
6. 看板和总看板（第十节）

## 十、同步看板和总看板

全部项目的文档写完、汇报后，接着做：

- **已安装 outline-board-sync**：对本次更新过的**每个**项目，按该技能做一次增量同步；同步依据的会议是这个项目的本次子文档（`meeting` 的 label＝子文档标题，取自首页第一行）。有镜像关系的，先同步原条目所在的项目，再同步写镜像行的项目。看板按同一个 Outline token 记下是谁、在什么时候同步的。
- 登记项目、首次创建「看板」文档（征得同意）、是否加入总看板（按项目已存的设置；首次登记时问，文档集全员可见时建议加入、私有时建议不加入）、同步后核对总看板，都由 outline-board-sync 负责，本技能不另外问。几个项目都要首次询问时，一次问完。
- **总看板**是看板服务按各项目实时汇总的页面（`/o`），不需要另外写入。Outline 里的「总看板」是一篇文档（不是文档集），只嵌着这个页面，放在哪由管理员决定；它的链接由 outline-board-sync 从看板服务取得，不要自己去搜，也不要编辑它。「同步总览」＝加入总看板的项目都已同步，并且在总看板上看得到；全部项目同步完再核对一遍。
- 某个项目同步失败（如没有编辑权限、dryRun 有待确认）不影响其他项目，在汇报里列出。
- 汇报末尾附上：每个项目的看板链接、「看板」文档链接、是否在总看板；总看板的链接（`/o` 页面和「总看板」文档；文档还没初始化时，照 outline-board-sync 的汇报写）。
- **未安装**：在汇报里提一句「看板和总看板没有同步，安装 outline-board-sync 后可以同步」，不自行安装。
