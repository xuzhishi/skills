# Outline 会后同步（会议纪要 → 进度追踪 / 待办事项 / 项目文档）

## 概述

本 skill 把"根据一份 Outline 会议纪要，同步更新项目文档"的完整流程标准化：

1. **定位并阅读会议纪要**：用 Outline MCP 读取全文，理解会议主题、结论、决策、待办、责任人、风险与时间节点
2. **定位并阅读项目文档**：找到会议所属项目的「进度追踪」「待办事项」「项目文档」目录及其全部相关文档，理解现状
3. **深度分析**：逐条拆解会议内容，判断每项内容应更新到哪个文档，并评估现有文档的内容与质量
4. **更新进度追踪**：里程碑、各任务状态、关键结论
5. **更新待办事项**：新增/更新待办，@ 责任人
6. **按需更新项目文档**：会议决策影响需求、架构、设计时，同步更新 PRD 等项目文档
7. **校验与汇报**：确认会议纪要未被改动，向用户汇报更新摘要

核心原则：**只新增和更新目标文档，绝不删改会议纪要；产出完整全面，细节不丢；有疑问先问，不猜。**

## 一、定位并阅读会议纪要

1. 用户给出会议纪要的 **URL 或标题**，用 Outline MCP 的 `fetch`（resource=document）读取全文
2. 仔细阅读并逐项记录：
   - 会议主题、时间、参会人/发言人
   - 会议摘要与核心结论
   - 逐条决策事项（含被否定/变更的旧方案，这能解释文档里旧内容的来龙去脉）
   - 逐条待办事项 + 责任人
   - 风险点、时间节点、未决事项
3. 阅读时留意**具体发言人姓名**（用于后续 @ 提及）；若只有「发言人1」「Rooms会议室-发言人N」等匿名标签，记下这一点，稍后向用户确认对应关系

## 二、定位并阅读项目文档

1. 从会议纪要元数据拿到 `collectionId`、`parentDocumentId`、breadcrumb，确定会议所属的**项目目录**
2. 用列文档树工具（如 `list_collection_documents`）列出项目目录结构
3. 按「目录约定」找到三类目标文档，**全部读取**：
   - 进度追踪
   - 待办事项
   - 项目文档目录下的所有文档（PRD、需求、设计等，含子文档）
4. 相关但未读的文档也要读（如更早的会议纪要、关联 PRD），避免遗漏上下文

### 目录约定

项目目录（如「成人抑郁」）下应有：

| 文档/目录 | 类型 | 用途 |
| --- | --- | --- |
| 进度追踪 | 文档 | 里程碑 + 各任务/模块当前状态 + 关键结论 |
| 待办事项 | 文档 | 待办清单、责任人、风险 |
| 项目文档 | 容器 | 内含 PRD 等需求/设计文档 |
| 会议纪要 | 容器 | 按日期归档的会议纪要 |

- **缺失处理**：找不到「进度追踪」「待办事项」「项目文档」时，向用户说明后自动创建（`create_document`，挂到项目目录下）
- 创建前告知用户将创建什么、挂在哪里，征得同意后执行

## 三、深度分析

逐条处理会议纪要内容，建立「更新映射」：

| 会议纪要内容 | 落点 |
| --- | --- |
| 决策与结论 | 进度追踪（关键结论）和/或项目文档（需求变更） |
| 待办事项 | 待办事项文档（新增条目、更新状态、@ 责任人） |
| 风险与时间节点 | 进度追踪（里程碑）和待办事项（风险） |
| 模块/任务进展表述 | 进度追踪中各任务的状态 |

同时**评估现有文档的内容与质量**，更新后的文档质量必须高于更新前：

- 旧内容与会议结论冲突的 → 标注并更新，同时保留变更脉络（何时因何会改）
- 会议纪要里已澄清、但文档里仍是问号/待定的 → 补全
- 缺章节、缺细节的 → 按会议内容补全
- 结构混乱的 → 重组为清晰层级（会议纪要的正文结构可作为重组依据）
- 写出来的更新必须**完整全面**：会议纪要里涉及的细节（数值、参数、时间、命名、设计点、引导语等）一条不落地落到对应文档

## 四、更新进度追踪

结构建议：

- 里程碑（时间表；会议确认的节点必须写入）
- 模块/任务进度表（状态 + 说明，依据会议纪要中的进展表述）
- 本次会议关键结论（逐条）

要求：

- **增量更新**：保留旧内容中仍有效的信息，叠加会议新结论，不覆盖丢失已有信息
- 会议纪要中提到的每个模块/任务都要有状态反映

## 五、更新待办事项

- 会议纪要中的待办**逐条写入**，保留原表述细节，不合并、不缩写
- 责任人有具体姓名 → @ 提及
- 更新已有待办的状态（完成/进行中）
- 风险、时间节点单独成节

## 六、按需更新项目文档

当会议纪要中的决策**改变需求、架构、设计细节**时（如模块更名、交互逻辑调整、新增模块、性能指标变化），同步更新项目文档（PRD 等）：

- 用 `update_document` 更新，保留原有全部内容与图片/链接资产（replace 重写时图片 URL 必须原样保留）
- 新增决策用「★ 会议日期 更新」标注，保留旧表述作为历史参考
- 命名/架构等硬变更直接改写，同时注明来源会议
- 不影响需求的内容（如纯排期讨论）不要硬塞进 PRD

## 七、@ 提及（mentions）

- 会议纪要中出现**具体发言人姓名**（真实用户名）→ 在进度追踪、待办事项的对应条目中 @ 该人
- 用 `list_users` 查询 Outline 用户列表，把会议纪要中的姓名匹配到用户（留意同名、昵称、拼音等情况）
- mention 写法：`@显示名`；若写入后未渲染为提及，至少保证姓名文本清晰可见，并在汇报中说明
- 只有「发言人1」「Rooms会议室-发言人N」等匿名标签、无法对应真实用户 → **主动询问用户**对应关系，不要乱 @

## 八、规范与安全

- **绝不修改会议纪要**：不编辑、不覆盖、不删除会议纪要及其任何内容
- 任何不清晰之处（模块归属、责任人、命名歧义、目标文档位置）→ **先问用户**，不猜
- 破坏性操作（删除/移动文档）前必须确认
- 更新完成后向用户汇报：改了哪些文档、主要变更点、遗留问题

## 九、完成后汇报

向用户列出：

1. 更新的文档及链接
2. 各文档的主要变更摘要
3. 遗留的疑问/待用户确认的点（如匿名发言人、有歧义的命名）
