# Outline 会后同步（会议纪要 → 进度与待办 / 项目文档）

## 概述

本 skill 把"根据一份 Outline 会议纪要，同步更新项目文档"的完整流程标准化：

1. **定位并阅读会议纪要**
2. **定位并阅读项目文档**：「进度与待办」首页、最近的会议子文档、「项目文档」
3. **深度分析**：逐条拆解会议内容，确定每项内容落到首页哪一行、子文档记哪种变化、是否影响项目文档
4. **新建会议子文档**：只记本次变化、本次决定、新增缺口
5. **重写「进度与待办」首页**：固定模板，当前全貌
6. **按需更新项目文档**
7. **校验与汇报**：确认会议纪要未被改动，向用户汇报
8. **同步看板（可选）**：若已安装 outline-board-sync，接着做一次增量同步

核心原则：**只新增和更新目标文档，绝不删改会议纪要；首页写当前全貌，子文档只记变化；有疑问先问，不猜。**

## 一、定位并阅读会议纪要

1. 用户给出会议纪要的 **URL 或标题**，用 Outline MCP 的 `fetch`（resource=document）读取全文
2. 仔细阅读并逐项记录：
   - 会议主题、时间、参会人/发言人
   - 会议摘要与核心结论
   - 逐条决策事项（含被否定/变更的旧方案，这能解释文档里旧内容的来龙去脉）
   - 逐条待办事项 + 责任人
   - 风险点、时间节点、未决事项
3. 阅读时留意**具体发言人姓名**（用于后续 @ 提及）；若只有「发言人1」「Rooms会议室-发言人N」等匿名标签，记下这一点，稍后向用户确认对应关系
4. 纪要标题形如 `YYYY-MM-DD 会议主题`；旧纪要在日期目录下，标题形如 `HH:MM-HH:MM 主题`，两种都认。

## 二、定位并阅读项目文档

1. 从会议纪要元数据拿到 `collectionId`、`parentDocumentId`、breadcrumb，确定会议所属的**项目目录**
2. 用列文档树工具（如 `list_collection_documents`）列出项目目录结构
3. 找到并读取：
   - 「进度与待办」首页全文（它就是上一版，写新版前必须读）
   - 「进度与待办」的子文档列表，以及最近几篇子文档（查编号、查决定）；编号要取「当天已用的最大号」时，读全部子文档
   - 「项目文档」目录下的所有文档（PRD、需求、设计等，含子文档）
4. 相关但未读的文档也要读（如更早的会议纪要、关联 PRD），避免遗漏上下文

### 目录约定

| 文档/目录 | 类型 | 用途 |
| --- | --- | --- |
| 看板 | 文档 | 看板服务生成的嵌入页面，**不要编辑** |
| 进度与待办 | 文档 | 首页＝当前全貌（里程碑、模块、风险、缺口、待办）；子文档＝每次会议的变化「YYYY-MM-DD 会议主题」 |
| 项目文档 | 容器 | 内含 PRD 等需求/设计文档 |
| 会议纪要 | 容器 | 会议纪要，一层：「YYYY-MM-DD 会议主题」 |

- **旧结构**（有「进度追踪」「待办事项」、没有「进度与待办」）：先不更新。告诉用户这个项目需要迁移，按 `references/migration.md` 出迁移计划；用户同意、迁移完成后再做本次会后更新。用户不同意迁移就停下，**不再按旧格式写**。
- **迁移没做完**（「进度与待办」和「进度追踪」或「待办事项」同时存在）：停下问用户。
- **都没有**：告诉用户将在项目目录下创建「进度与待办」（和「项目文档」，如果也没有），征得同意后创建；不再创建「进度追踪」「待办事项」。

## 三、深度分析

逐条处理会议纪要内容，建立「更新映射」：

| 会议纪要内容 | 落点 |
| --- | --- |
| 决策与结论 | 会议子文档「本次决定」，和/或项目文档（需求变更） |
| 待办事项 | 首页「待办」（每条原始待办一行），子文档记「新增」 |
| 缺负责人、缺日期、移交不明 | 首页「缺口」 |
| 风险与时间节点 | 首页「里程碑」「风险」 |
| 模块/任务进展表述 | 首页「模块」等各行的状态和进展，子文档记对应的变化 |

同时**评估现有文档的内容与质量**，更新后的文档质量必须高于更新前：

- 旧内容与会议结论冲突的 → 按新结论改写首页，并在子文档记一行变化（原→新、原因、提出人）
- 会议纪要里已澄清、但文档里仍是问号/待定的 → 补全
- 缺章节、缺细节的 → 按会议内容补全
- 结构混乱的 → 重组为清晰层级（会议纪要的正文结构可作为重组依据）
- 写出来的更新必须**完整全面**：会议纪要里涉及的细节（数值、参数、时间、命名、设计点、引导语等）一条不落地落到对应文档。首页和子文档只写结论和事实；数值、参数、讨论细节写进项目文档（第六节），或者留在纪要里。

## 四、重写「进度与待办」首页（固定模板）

首页是项目的**当前全貌**，每次会后按 `references/progress-doc-template.md` 整篇重写。写之前先读完这个文件。

- **骨架**：页首两行引用块 + 里程碑、模块、风险、缺口、待办五张表 + 「最近会议」清单；表头一律是 `| 编号 | 事项 | 负责人 | 截止 | 状态 | 进展 | 关联 |`；不写 H2、`---`、段落、卡片、本次决定、历史部分。
- **一件事只写一行**，别处只写编号。
- **全量重写**：上一版所有没关闭的编号都要再出现，每一栏都写全；本次关闭的条目在表尾保留一次，下次重写时删去。
- **单一负责人**：负责人格里恰好一个人，其余的人写成「（执行：…）」；汇报人不是负责人，只有会上明确移交才换人；定不下来先问用户，还是定不下来就写「待指定（见 编号）」并建一条缺口行。
- **具体截止**：相对说法按会议日期换算成最晚的那一天，原话写在括号里；改期时累加「原 M/D」，进展里写「延期：原因（提出人）」；没有日期的写「待定（见 编号）」并建缺口行；只有会上明确决定不设日期，才写「无承诺」。
- **缺口**：缺负责人、缺日期、移交不明，都在「缺口」表建一行正式待办，有负责人（项目负责人或原行负责人）、截止默认下次例会，会同步到看板、过期也算逾期；AI 自己拿不准的事（转写里点的是谁、发言人是谁）当场问用户，不建缺口行。
- **状态**：只用六个词——未开始、进行中、阻塞、待核实、已完成、暂停·取消，不因为日期已过而改状态。
- **编号**：遵守「八」里的「保留看板编号」；所有新编号（待办和缺口的 `MMDD-NN`，模块、里程碑、风险的 `K`/`M`/`R`）在写入前由本技能编好，不留空。
- **写入**：先建第五节的会议子文档，再用 `update_document` 整篇重写首页，标题不变；已有的提及链接从 `fetch` 结果原样复制。写入前按模板文件的「自检」（第 27 条）逐项检查，写入后重新 `fetch` 核对。

## 五、新建会议子文档（只记本次变化）

- 每次会后在「进度与待办」下新建**一篇**，标题与会议纪要标题逐字相同（`YYYY-MM-DD 会议主题`）；先建子文档，再重写首页，首页页首链接到它。
- 内容只有三节：「本次变化」表（`| 编号 | 事项 | 变化（原→新） | 原因 · 提出人 | 依据〔mm:ss〕 |`，类型为新增、恢复、换负责人、改期、改完成标准、改状态、关闭、进展）、「本次决定」（拍板人、否决的方案、影响的编号）、「新增缺口」。不写全量快照，人名不写 @。
- 「本次变化」必须和首页新旧两版的差异一一对应，规则见模板文件。
- `create_document` 会把新子文档放在最上面；补建较早会议的子文档时，用 `move_document` 的 `index` 排到正确位置（新的在上）。同一父文档里往下移时 `index` 要按移动前的位置算，取法见模板文件第 24 条，不要直接传「比它新的篇数」。
- 纪要还在旧日期目录里（标题 `HH:MM-HH:MM 主题`）时，子文档标题用 `YYYY-MM-DD 主题`（日期取日期目录），见模板文件第 20 条。
- 子文档建好后不再修改。发现错误时，经用户同意用 patch 更正，并在文末加一行「更正：…」。同一场会已经有子文档时不再新建。
- 纪要里的每条原始待办在首页各占一行，不合并；标题取原句，只去掉时间词、@ 和句末标点。

## 六、按需更新项目文档

当会议纪要中的决策**改变需求、架构、设计细节**时（如模块更名、交互逻辑调整、新增模块、性能指标变化），同步更新项目文档（PRD 等）：

- 用 `update_document` 更新，保留原有全部内容与图片/链接资产（replace 重写时图片 URL 必须原样保留）
- 新增决策用「★ 会议日期 更新」标注，保留旧表述作为历史参考
- 命名/架构等硬变更直接改写，同时注明来源会议
- 不影响需求的内容（如纯排期讨论）不要硬塞进 PRD
- 决策写进项目文档后，在当次子文档「本次决定」那一条后面附上链接

## 七、@ 提及（mentions）

- @ 只写在首页的「负责人」格里（负责人本人和「执行」里的人，写法 `@[姓名](mention://user/<userId>)`）；已有的提及从 `fetch` 结果原样复制，不要改成两段写法，否则每次重写都会重新通知所有人。首页其他地方和会议子文档里的人名一律写纯文本。
- 用 `list_users` 查询 Outline 用户列表，把会议纪要中的姓名匹配到用户（留意同名、昵称、拼音等情况）
- 没有 Outline 账号的人写纯文本 `@姓名`，并在汇报中列出；写入后重新 `fetch`，提及没有渲染出来的，也在汇报中说明
- 只有「发言人1」「Rooms会议室-发言人N」等匿名标签、无法对应真实用户 → **主动询问用户**对应关系，不要乱 @；用户确认后记进当次子文档页首的「身份确认」

## 八、规范与安全

- **绝不修改会议纪要**：不编辑、不覆盖、不删除会议纪要及其任何内容
- 任何不清晰之处（模块归属、责任人、命名歧义、目标文档位置）→ **先问用户**，不猜
- 破坏性操作（删除/移动/归档文档）前必须确认
- 更新完成后向用户汇报：改了哪些文档、主要变更点、遗留问题
- **保留看板编号**：「进度与待办」首页和会议子文档里的编号（待办、缺口 `MMDD-NN`，模块 `K01`，里程碑 `M01`，风险 `R01`）是看板同步用的稳定标识。首页「编号」列不得删除、清空、改写，也不得挪到别的条目上；已关闭、从首页删去的编号也不再使用。新编号由本技能按模板文件编好，接着已用的最大号往下编，能调用看板时与 `board_next_code` 的结果取大。
- **不要编辑「看板」文档**：它由看板服务生成，只有一个嵌入，markdown 写入会把嵌入变成普通链接。
- **会议子文档只写一次**：除经用户同意的更正外，不修改已有的子文档。
- **不重建旧文档**：不再创建「进度追踪」「待办事项」；遇到旧结构先迁移（`references/migration.md`）。迁移中的每一次写入（改名、重写首页、建子文档、移动或改名纪要、归档）都要先给用户看，得到同意后执行。

## 九、完成后汇报

向用户列出：

1. 更新的文档及链接：本次会议子文档、「进度与待办」首页、改动过的项目文档
2. 主要变更摘要
3. 本次延期（编号，原日期→新日期）、逾期未汇报和连续 2 次未提及的行、新建的缺口行、带「（拟）」的完成标准
4. 遗留的疑问/待用户确认的点（匿名发言人、点了多人、说法冲突、没有 Outline 账号的人）

## 十、同步看板（可选）

汇报完成后：

- 若当前环境已安装 outline-board-sync 技能，接着按该技能做一次**增量同步**，以本次会议子文档作为同步依据的会议，并在汇报末尾附上看板链接
- 未安装则跳过，不必提示安装
- 首次登记项目、创建「看板」文档、是否加入总看板等询问，都由 outline-board-sync 负责
